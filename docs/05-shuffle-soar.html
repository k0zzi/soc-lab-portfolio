This post documents the fifth chapter of the SOC Lab build series. Chapter 4 brought network-layer threat detection and active blocking online with Suricata IPS. This chapter brings the SOAR (Security Orchestration, Automation and Response) layer online: Wazuh alerts get forwarded to Shuffle, which analyzes them, automatically updates OPNsense, and sends notifications over Telegram.

This chapter covers a lot of ground: setting up Shuffle, integrating the OPNsense API, writing a Wazuh custom rule, and building two separate workflows. Each piece gets its own section, since each has its own quirks.

ℹ
Prerequisite A working OPNsense, Wazuh, and Suricata environment is required. Chapters 2, 3, and 4 must already be complete. OPNsense API access and SSH access to the Wazuh Manager are both used in this chapter.
Architecture

What Changed in This Chapter?

In previous chapters, every detection and blocking system ran independently. This chapter has Shuffle tie them together through orchestration: alerts Wazuh generates get forwarded to Shuffle, which runs its own logic and updates OPNsense.

Step 02

Webhook Security and Initial Configuration

Shuffle's webhooks are open to anyone by default — any IP can send a request. Even in a lab environment, that's not acceptable; nothing but Wazuh should be able to hit these webhooks.

Token-Based Authentication

"Require Authentication" was enabled on every workflow's webhook. Shuffle generates a token; requests without it are rejected.

Test without a tokencurl -X POST http://10.1.30.11:3001/api/v1/hooks/WEBHOOK_ID
# Response: {"success": false}  ← correct behavior

Test with a tokencurl -X POST http://10.1.30.11:3001/api/v1/hooks/WEBHOOK_ID \
  -H "Authorization: Bearer TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"test": "data"}'
# Response: {"success": true}  ← accepted
ℹ
Run Limit Even though Shuffle is open-source, it keeps a cloud-linked usage counter: 25,000 runs/month. Once that's exceeded, it throttles to 1 execution per minute. During development, testing burns through this limit fast — every workflow run counts. It's not an issue at normal alert frequency in production, but it's worth watching closely during setup and debugging.
Step 03

OPNsense Integration: API, Alias, and Floating Rule

Shuffle manages OPNsense through its API. Two operations happen: add the attacking IP to an alias, then apply that change to the firewall. A floating rule referencing that alias enforces the block across all traffic.

Creating an API Key

1

Get an API Key in OPNsense

System → Access → Users → Admin → API keys tab → Add. This generates a Key and a Secret — the Secret is shown only once and needs to be saved immediately.

2

Define the Credential in Shuffle

In Shuffle: Settings → Credentials → New credential. Authentication type: HTTP Basic Auth. Username: the API Key, Password: the API Secret. Name: opnsense-api.

Creating the Alias

In OPNsense: Firewall → Aliases → Add:

shuffle_blocked_IPs Alias
Nameshuffle_blocked_IPs
TypeHost(s)
ContentEmpty at first — Shuffle populates it
DescriptionIPs blocked automatically by Shuffle SOAR

The Floating Rule

The alias doesn't do anything on its own. Without a firewall rule that references it, no IPs get blocked. Firewall → Rules → Floating → Add:

Floating Rule — Shuffle Auto-Block
ActionBlock
Directionin
InterfaceWAN, VLAN10, VLAN20, VLAN30, VLAN60, VLAN70 — all of them
Sourceshuffle_blocked_IPs
Destinationany
DescriptionShuffle SOAR Auto-Block
ℹ
Why a Floating Rule? An interface-specific rule only affects traffic coming from that one interface. A floating rule applies to every interface at once — the same rule blocks Kali on VLAN70 just as well as a genuine attacker IP coming in from outside. Any IP Shuffle adds to the alias gets blocked instantly, no matter which interface it arrives on.

API Endpoints

Shuffle's block-ip node makes two API calls:

OPNsense API — Add an IPPOST /api/firewall/alias_util/add/shuffle_blocked_IPs
Content-Type: application/json
Body: {"address": "10.1.70.10"}

# Successful response: {"status": "done"}

POST /api/firewall/alias/reconfigure
# Apply the change to the firewall — without this call, the alias doesn't take effect
⚠
SSL Verify Disabled Since OPNsense uses a self-signed certificate, SSL Verify was disabled on the Shuffle HTTP node. Acceptable for a lab environment — production should use a signed certificate instead.

Step 04

Wazuh Integration: Custom Rule and ossec.conf

Two things need to happen for Wazuh to send alerts to Shuffle: adding an integration block to ossec.conf, and writing a custom rule that only catches port-scan alerts.

Custom Rule 100100: Why It's Needed

Every Suricata alert lands under rule ID 86601 in Wazuh. Pointing the integration at that rule would send every Suricata alert to Shuffle — malware detections, policy violations, DNS queries, all of it. That's both wasteful given the run limit and beyond the scope of the port-scan workflow.

The fix: write rule 100100 as a child of 86601. This rule only fires on alerts where the alert.signature field contains "SCAN". ET Open's port-scan rules all start with "ET SCAN" — this filter catches exactly what's needed.

⚠
The Wazuh Rule Field Name Trap In the Wazuh Dashboard, the field for Suricata alerts shows as data.alert.signature. But in the rule XML's <field> tag, the data. prefix isn't used — it's just alert.signature. The wrong prefix means the rule never fires, with no error at all — it fails silently. This mismatch between what the Dashboard displays and what the rule syntax expects cost hours of debugging. 
/var/ossec/etc/rules/local_rules.xml<group name="suricata,portscan,">
  <rule id="100100" level="10">
    <if_sid>86601</if_sid>
    <field name="alert.signature">SCAN</field>
    <description>Suricata: Port scan detected - $(alert.signature)</description>
  </rule>
</group>
ℹ
About the Wazuh Rule File An attempt was made to edit local_rules.xml from the Dashboard — it threw a validation error, because the Dashboard validates the entire Wazuh configuration, including ossec.conf, at the same time. The file was edited via terminal instead: sudo nano /var/ossec/etc/rules/local_rules.xml. It can contain multiple <group> blocks — unlike the standard XML single-root-element rule, the Wazuh parser supports this. 
Wazuh Manager — Restart and Verifysudo systemctl restart wazuh-manager

# Run an nmap scan from Kali, then query the Dashboard:
rule.id:100100
# If the alert shows up, the rule is working

ossec.conf: Two Integrations

Two separate webhooks were set up: a general notification channel forwarding all level 10+ alerts to Telegram, and a dedicated channel forwarding only port-scan alerts to the port-scan-auto-block workflow.

/var/ossec/etc/ossec.conf<!-- Workflow 1: All level 10+ alerts — Telegram notification -->
<integration>
  <name>shuffle</name>
  <hook_url>http://10.1.30.11:3001/api/v1/hooks/WEBHOOK_ID_1</hook_url>
  <level>10</level>
  <alert_format>json</alert_format>
</integration>

<!-- Workflow 2: Port-scan alerts only — automatic block -->
<integration>
  <name>shuffle</name>
  <hook_url>http://10.1.30.11:3001/api/v1/hooks/WEBHOOK_ID_2</hook_url>
  <rule_id>100100</rule_id>
  <alert_format>json</alert_format>
</integration>
ℹ
Using Level and Rule_ID Together When <level> and <rule_id> are both set on a Wazuh integration, both conditions have to be satisfied (an AND). Rule 100100 is defined at level 10, but when the two conditions are combined, no alert comes through — only <rule_id> is needed; <level> should be removed. 
Restartsudo systemctl restart wazuh-manager

Step 06

Workflow 2: port-scan-auto-block

This workflow has one job: detect the IP running a port scan, protect the infrastructure components, block everything else in OPNsense, and open a case in TheHive. It has four nodes: webhook, Python analysis, HTTP block, and TheHive case creation.

Webhook → portscanconfig → condition → BLOCK → block-ip → TheHive case
INTERNAL → no action

portscanconfig: The Python Analysis Node

The Python node extracts the source IP from inside the Wazuh alert and checks it against a whitelist. Infrastructure components (OPNsense, Wazuh, Shuffle, the AD servers) are whitelisted — traffic from them is never blocked. Every other IP gets blocked: internal clients, Kali, external sources, all of it.

⚠
The Shuffle Python Node's $exec Trap The json.loads("""$exec""") approach in Shuffle's Python execute node fails on some alerts. If the JSON Wazuh sends contains special characters (quotation marks, backslashes), it breaks Python's triple-quoted string and causes a parse error. The failure gets silently swallowed and returns NO_IP. The fix: use Shuffle's native Python API, self.full_execution, instead. 
portscanconfig — Python Scriptimport json

# self.full_execution["execution_argument"] returns the Wazuh alert as a dict
# The json.loads("""$exec""") approach breaks on special characters in Suricata's signature field
alert = self.full_execution["execution_argument"]

try:
    src_ip = alert["all_fields"]["data"]["src_ip"]
except:
    src_ip = None

if src_ip:
    # Infrastructure components — never blocked
    whitelist = [
        "10.1.10.5",   # OPNsense
        "10.1.30.1",   # VLAN30 gateway
        "10.1.30.10",  # Wazuh
        "10.1.30.11",  # Shuffle
        "10.1.20.10",  # SRV201 DC
        "10.1.20.11",  # SRV202
    ]
    if src_ip in whitelist:
        print(json.dumps({"category": "INTERNAL", "ip": src_ip}))
    else:
        print(json.dumps({"category": "BLOCK", "ip": src_ip}))
else:
    print(json.dumps({"category": "NO_IP", "ip": ""}))

block-ip: The OPNsense HTTP Node

block-ip — URLhttps://10.1.10.5/api/firewall/alias_util/add/shuffle_blocked_IPs

block-ip — Body{"address": "$exec.all_fields.data.src_ip"}

block-ip — Reconfigure URLhttps://10.1.10.5/api/firewall/alias/reconfigure
# Without this call, the alias updates but never reaches the firewall
ℹ
The Variable Used in block-ip Rather than portscanconfig's output ($portscanconfig.message.ip), $exec.all_fields.data.src_ip was used directly. Both resolve to the same value, but the $exec variable resolves more reliably inside HTTP nodes.

"Suricata drops the packet instantly. Shuffle blocks the IP permanently. Both respond to the same threat, at different layers."

Troubleshooting

Problems Hit During Setup

ProblemCauseFix
Workflow executions time out Shuffle retries failed executions by default, ending up in a loop Added SHUFFLE_DISABLE_RERUN_AND_ABORT=true to docker-compose.yml
block-ip returns a "nonexistent alias" error The alias name was mistyped in the URL: shuffle_blocked_IPsD (an extra D) Fixed the URL: /alias_util/add/shuffle_blocked_IPs
block-ip returns a 500 error, "Unexpected error" The IP variable in the body was written as $$exec.all_fields.data.src_ip — the double $ turned the value into $10.1.70.10 Used a single $: $exec.all_fields.data.src_ip
portscanconfig always returns NO_IP A special character in the Suricata alert signature broke json.loads("""$exec""") Switched to self.full_execution["execution_argument"] — Shuffle's native API
Wazuh rule 100100 never fires Written as <field name="data.alert.signature"> — that's how it appears in the Dashboard, but the rule itself doesn't use the data. prefix Fixed to <field name="alert.signature"> — without the data. prefix
Using <level> and <rule_id> together stops alerts from arriving The two conditions are ANDed together in a Wazuh integration — rule 100100 is at level 10, but requiring both at once blocks the match Removed <level>, kept only <rule_id>100100</rule_id>
Telegram: "Bad Request: message text is empty" An invisible whitespace character in the body field made the JSON invalid, leaving Telegram's text field empty Cleaned up and rewrote the body without the stray whitespace
The IP never gets added to the alias, even though block-ip returns success OPNsense's response body says status:failed even on requests it actually accepts — Shuffle was treating that as a success Inspected OPNsense's response body directly, found both the alias-name typo and the variable-path issue
local_rules.xml can't be saved from the Dashboard The Dashboard validates the entire Wazuh configuration on save — it fails if there's an error anywhere else Edited it via terminal instead: sudo nano /var/ossec/etc/rules/local_rules.xml
A hyphen (-) in the Python node's name causes problems A node named port-scan-config was incompatible with Shuffle's templating engine — variable references couldn't resolve Renamed the node without a hyphen: portscanconfig
