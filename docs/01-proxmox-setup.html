Building a SOC Lab From Scratch:
Proxmox, VM Configuration, and Remote Access

From a bare-metal machine to a virtual lab environment: Proxmox installation, disk configuration, Windows and Ubuntu VMs, and secure remote access with Tailscale.

~15 min read · Level: Beginner–Intermediate · Proxmox VE 8.x

This post documents the notes from building an actual SOC lab environment. It isn't a theoretical guide — it's a record of the decisions made, the problems hit, and the fixes applied while installing Proxmox VE on physical hardware.

Active Directory, Wazuh, OPNsense, and more will be built on top of this foundation in later chapters. Everything starts here.

ℹ
About the Hardware This lab was built on a desktop machine with an AMD Ryzen 5 1600 CPU, 32 GB of RAM, and a Samsung 970 Evo Plus 1 TB NVMe SSD.

Update: this machine was later upgraded to a Ryzen 9 9950X3D / 96 GB DDR5 configuration. The original hardware was repurposed as a second physical node (SRV-RED), covered in a later phase of the project.

Step 01

Installing Proxmox VE

Proxmox Virtual Environment (PVE) is an open-source, Debian-based virtualization platform. It ships with both KVM (full virtualization) and LXC (container) support, along with a web-based management interface. The reasons for choosing it for this SOC lab were straightforward: it's simple to install, uses resources efficiently, and its snapshot capabilities make the break-fix cycle far easier to manage.

⚠
Why Not VMware ESXi? VMware ESXi was evaluated before settling on Proxmox, but the installation couldn't be completed because ESXi didn't support the available Ethernet card. ESXi's supported NIC list is fairly restrictive, and working around it requires driver injection into the installer ISO. Proxmox was chosen instead because it offers much broader hardware support.

Pre-Installation BIOS Settings

A few BIOS settings need to be configured correctly before starting the installation. Skipping this step was observed to cause the installer to hang at the "Make system bootable" stage.

1

Boot Mode Set to UEFI

In the BIOS, "Boot Mode" was set to UEFI only, and CSM (Compatibility Support Module) was set to Disabled. This step is critical if installing with ZFS.

2

Secure Boot Disabled

Under the "Security" tab, Secure Boot → Disabled was set. This can be revisited after Proxmox is installed, but it must be off during installation.

3

Virtualization Support Enabled

Since an AMD CPU was used, SVM Mode → Enabled was verified. Intel users need to confirm Intel VT-x → Enabled instead. KVM won't work without this.

Downloading the ISO and Preparing a Boot USB

The Proxmox VE ISO was downloaded from proxmox.com/en/downloads and written to a USB drive prepared with Ventoy. Rufus or Balena Etcher would work just as well, but Ventoy turned out to be more practical since it can carry multiple ISOs at once instead of requiring the USB to be rewritten each time.

⚠
Warning: All Data on the Disk Will Be Erased The Proxmox installer completely wipes the selected disk. Any data on it that needs to be kept should be backed up before starting. This cannot be undone.

Choosing a Filesystem

The installer prompts for a filesystem choice. Two options were considered for this lab:

Filesystem Advantages Drawbacks Recommendation
ZFS (RAID0) Checksummed data integrity, fast snapshots, compression Aggressive memory use, reducing RAM available to VMs Alternative
ext4 Lightweight, stable, low resource use, snapshot support Lacks ZFS's advanced integrity checking and compression Recommended

ext4 was chosen for the SOC lab. ZFS's snapshot and data-integrity features are appealing, but its memory footprint would have significantly cut into the RAM available for VMs on this hardware. Since Proxmox can still take VM-level snapshots on ext4, this wasn't a real drawback.

ℹ
Disk Configuration Deferred The disk settings on the installer screen were left at their defaults at this stage. Partitioning and configuring the storage pools was done through the Proxmox web interface after installation.

Post-Installation Setup

After Proxmox finished installing and rebooted, the web interface was reached at https://192.168.1.50:8006. Two important settings were handled on first login:

The enterprise-repository warning and the switch to the no-subscription repository were both handled through the interface rather than the terminal. Under Node → Repositories in the Proxmox web UI, the enterprise repository was disabled and the no-subscription repository was added. System updates were then applied from the Updates tab.

Step 03

Disk Configuration

The disk layout was designed as two separate storage pools during installation. The Samsung 970 Evo Plus 1 TB NVMe drive was partitioned and brought into use through the Proxmox interface.

100 GB was allocated to the Proxmox system itself. The remaining space was split into two storage pools: arch.srv, sized at 100 GB for archival purposes such as ISO storage; and prod.srv, set aside as the main storage pool for VM disks and snapshots.

Storage Layout
System (Proxmox)100 GB · ext4
arch.srv100 GB · ISO and archive storage
prod.srvRemaining space · VM disks and snapshots

Uploading ISO Files

ISO files need to be uploaded to Proxmox before a VM can be created. From the interface: SRV → local (arch.srv) → ISO Images → Download from URL lets you paste an ISO's download link and pull the file straight into Proxmox. This avoids the extra step of downloading the ISO to a local machine first and then uploading it.

Once the Windows installations were complete, the QEMU Guest Agent was installed from the mounted VirtIO ISO. This lets Proxmox see the VMs' IP addresses and enables RAM ballooning and KSM sharing. By the end of this stage, 2 Windows Server instances and 1 Windows 11 Enterprise client had been installed.

No network adapter was added to the VMs at this stage. Since internet access would be provided through OPNsense, this step was deferred until the right network interface was in place.

Step 05

Ubuntu VM Setup

Configuration for Ubuntu was much simpler than for Windows — none of the extra steps around TPM or VirtIO driver compatibility were needed.

A second network interface named vmbr1 was created in Proxmox before installing the Ubuntu VM. This bridge wasn't connected to any physical port — it acts as a virtual switch that will serve as OPNsense's LAN leg. Internet traffic reaches OPNsense from the physical NIC via vmbr0, and OPNsense distributes it to the internal network over vmbr1. Once OPNsense is set up, this leg will be segmented by VLAN, each with its own firewall rules.

Step 06

Remote Access with Tailscale

Even though the lab is physically reachable from devices on the same network, a secure way to keep working remotely was needed — without opening any inbound ports and creating a security exposure. Tailscale was chosen for this.

Tailscale is a mesh VPN built on the WireGuard protocol. Devices find each other directly, even behind NAT, and connect over an encrypted tunnel. It was set up in seconds with a Google account, with no additional server required.

Installing Tailscale on Proxmox

Proxmox Shell# Add the Tailscale repository
curl -fsSL https://pkgs.tailscale.com/stable/debian/bookworm.noarmor.gpg \
  | tee /usr/share/keyrings/tailscale-archive-keyring.gpg > /dev/null

curl -fsSL https://pkgs.tailscale.com/stable/debian/bookworm.tailscale-keyring.list \
  | tee /etc/apt/sources.list.d/tailscale.list

# Install the package
apt update && apt install tailscale -y

# Start Tailscale — generates a browser link for signing in with a Google account
tailscale up

Running the command produced a URL in the terminal. Opening it in a browser and signing in with a Google account added the Proxmox node to the Tailscale network and assigned it a Tailscale IP address (typically in the 100.x.x.x range).

Setting Up Tailscale with a Google Account

1

Created a Tailscale Account

Went to tailscale.com and signed in with Google. The free plan is more than enough for a personal lab (up to 100 devices).

2

Added the Proxmox Node

Ran the install commands. After tailscale up, the resulting URL was visited to authorize with the Google account. The Proxmox node then appeared in the admin console.

3

Installed Tailscale on the Personal Computer Too

Downloaded Tailscale for Windows from tailscale.com/download and connected it with the same Google account. Both devices are now on the same Tailscale network.

4

Connected to Proxmox via Its Tailscale IP

The Proxmox node's Tailscale IP was found with tailscale ip -4. From there, the Proxmox web interface became reachable from anywhere at https://100.x.x.x:8006.

Proxmox Shell# Find the Tailscale IP
tailscale ip -4

# Check Tailscale connection status
tailscale status

# Make the Tailscale service start on boot
systemctl enable tailscaled
⚠
The Proxmox Interface Should Never Face the Internet Directly Exposing Proxmox directly to the internet without Tailscale — for example, by port-forwarding 8006 — carries serious security risk. In this lab, the Proxmox interface has always been accessed exclusively through Tailscale.
