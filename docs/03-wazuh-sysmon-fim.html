This post documents the notes from building an actual SOC (Security Operations Center) lab environment. It isn't an academic guide — it's a record of a setup process that was actively worked through, with mistakes made and fixed along the way.

The goal: in a Windows environment built on Active Directory, put together infrastructure that can detect attacks, centrally collect logs, and eventually support automated response.

ℹ
About the Environment This lab is designed to simulate a real corporate SOC. It's a comprehensive project involving VLAN segmentation, attack machines, and defensive tooling. This chapter covers only the Wazuh, Sysmon, and FIM setup.

Step 01

Installing Wazuh Manager

Wazuh is an open-source SIEM (Security Information and Event Management) platform. The Manager collects logs from agents, analyzes them, and generates alerts. The Dashboard is a Kibana-based interface built on Elasticsearch/OpenSearch.

Agent Rollout

Agents weren't installed manually in this lab — they were pushed out automatically via a script through Active Directory to every machine joined to the domain. The result was 3 active agents:

IDAgent NameIPGroupStatus
001SRV20110.1.20.10SRV● Active

Agent Groups

In Wazuh, agents are assigned to groups, and different configurations can be applied per group. Two groups were created for this lab: SRV (for servers) and CLT (for clients). This split makes it possible to apply different rules and monitoring policies to servers versus clients later on.

Step 02

Sysmon: Centralized Deployment via GPO

Sysmon (System Monitor) is a Windows system service developed by Microsoft Sysinternals. It produces far more detailed process, network, and file activity logs than Windows' default event logs. Combined with MITRE ATT&CK mapping, it becomes possible to match log data directly to attack techniques.

"Without Sysmon, Windows logs are like being blind. With Sysmon, the same environment suddenly becomes transparent."

Why Deploy via GPO?

Rather than installing Sysmon manually on every machine, a Group Policy Object (GPO) automatically installs it on every machine joined to the domain. When a new machine joins the domain, Sysmon installs itself automatically on its next restart. Config updates are also managed centrally.

Step 1: Share the Files

A D:\Sysmon folder was created on SRV201 and populated with the following files:

D:\Sysmon\
    ├── Sysmon64.exe        ← Microsoft Sysinternals
    ├── sysmonconfig.xml    ← Olaf Hartong sysmon-modular
    └── Install-Sysmon.ps1  ← Install script
ℹ
Choosing a Sysmon Config Olaf Hartong's sysmon-modular project is an ideal fit for this lab. With MITRE ATT&CK-mapped rules, a good whitelist/filter balance, and broad event coverage, it's a production-ready starting point.

The folder was shared as a network share at \\SRV201\Sysmon. Permissions:

GroupShare PermissionNTFS Permission
Domain AdminsFull ControlFull Control
Domain ComputersReadRead & Execute

Step 2: The Install Script

The script checks whether Sysmon is already installed. If not, it installs it; if it is, it updates the config instead:

Install-Sysmon.ps1$SysmonShare = "\\SRV201\Sysmon"
$SysmonExe   = "$SysmonShare\Sysmon64.exe"
$SysmonCfg   = "$SysmonShare\sysmonconfig.xml"
$LocalPath   = "C:\Windows\Sysmon64.exe"

$service = Get-Service -Name "Sysmon64" -ErrorAction SilentlyContinue

if ($null -eq $service) {
    Copy-Item $SysmonExe $LocalPath -Force
    Start-Process -FilePath $LocalPath -ArgumentList "-accepteula -i $SysmonCfg" -Wait
} else {
    Start-Process -FilePath $LocalPath -ArgumentList "-c $SysmonCfg" -Wait
}

Step 3: The GPO Wrapper (.bat)

A .bat wrapper was used for the GPO startup script to avoid running into PowerShell execution policy issues:

Install-Sysmon.bat@echo off
PowerShell.exe -ExecutionPolicy Bypass -File "\\SRV201\Sysmon\Install-Sysmon.ps1"

Step 4: GPO Configuration

1

Create the GPO

Group Policy Management → Group Policy Objects → New → Sysmon Deployment GPO

2

Add the Startup Script

Computer Configuration → Windows Settings → Scripts (Startup) → Scripts tab → Add → \\SRV201\Sysmon\Install-Sysmon.bat

3

Link the GPO to the Domain

Right-click soc.dev → Link an Existing GPO → Sysmon Deployment GPO

4

Also Link It to the Domain Controllers OU

DCs aren't affected by the default GPO link. A separate link needs to be added to the Domain Controllers OU.

⚠
Important: PowerShell Scripts vs. the Scripts Tab The GPO Startup screen has two tabs: PowerShell Scripts and Scripts. For a .bat file, the Scripts tab must be used, not the PowerShell tab. Otherwise the script won't run.

Verification

After a restart, check the service on any machine:

# Status: Running ✓
Step 03

Wazuh Agent Configuration

Sysmon was installed, but the Wazuh agents still need to be configured to read the Sysmon log channel. This configuration is applied per group from the Wazuh Dashboard — there's no need to touch each machine individually.

Agent Config for the SRV and CLT Groups

Management → Groups → the relevant group → Edit group configuration:

agent.conf<agent_config>

  <!-- Sysmon Logs -->
  <localfile>
    <location>Microsoft-Windows-Sysmon/Operational</location>
    <log_format>eventchannel</log_format>
  </localfile>

  <!-- Windows Security Logs -->
  <localfile>
    <location>Security</location>
    <log_format>eventchannel</log_format>
  </localfile>

  <!-- Windows System Logs -->
  <localfile>
    <location>System</location>
    <log_format>eventchannel</log_format>
  </localfile>

  <!-- PowerShell Logs -->
  <localfile>
    <location>Microsoft-Windows-PowerShell/Operational</location>
    <log_format>eventchannel</log_format>
  </localfile>

</agent_config>

Once the config was saved, the agents were restarted:

SSH — Wazuh Managersudo /var/ossec/bin/agent_control -R -a
✓
Result After the agent restart, Sysmon logs started flowing in from all three machines. A rule.groups: sysmon query in Wazuh Discover returned 8,500+ events, split CLT601: 55.8%, SRV201: 25.9%, SRV202: 18.3%.
Step 04

FIM: File and Registry Monitoring

FIM (File Integrity Monitoring) detects changes to critical files and registry keys in near real time. An attacker establishing persistence, evading defenses, or exfiltrating data has to change something — FIM catches those changes.

"Attackers prefer the deepest corners. Configuring FIM correctly means lighting up exactly the places they love most."

Design Decisions

DecisionReasoning
realtime=no on high-churn directoriesReal-time monitoring on directories like C:\Temp puts unnecessary load on the CPU
report_changes=yes only on critical pathsDiffing binary files wastes disk space for no benefit
Ignore .tmp .log .etlCuts system noise by 30–40%
Registry monitoring addedAttackers often use the registry instead of dropping files
Separate config for SRV and CLTThe AD server and clients carry different risks

SRV Group — Syscheck Configuration

agent.conf — SRV<syscheck>
  <disabled>no</disabled>
  <frequency>300</frequency>

  <!-- AD-critical — rarely changes, but critical when it does; realtime -->
  <directories check_all="yes" report_changes="yes" realtime="yes">
    C:\Windows\NTDS</directories>
  <directories check_all="yes" report_changes="yes" realtime="yes">
    C:\Windows\SYSVOL</directories>
  <directories check_all="yes" report_changes="yes" realtime="yes">
    C:\Windows\System32\GroupPolicy</directories>

  <!-- Registry hives (SAM, SYSTEM, SECURITY) -->
  <directories check_all="yes" report_changes="yes" realtime="yes">
    C:\Windows\System32\config</directories>

  <!-- Persistence locations -->
  <directories check_all="yes" report_changes="yes" realtime="yes">
    C:\Windows\System32\Tasks</directories>
  <directories check_all="yes" report_changes="yes" realtime="yes">
    C:\Windows\System32\drivers\etc</directories>
  <directories check_all="yes" report_changes="yes" realtime="yes">
    C:\Windows\System32\WindowsPowerShell</directories>

  <!-- High-churn directories — periodic scan only -->
  <directories check_all="yes" report_changes="no">
    C:\Windows\Temp</directories>
  <directories check_all="yes" report_changes="no">
    C:\ProgramData</directories>

  <!-- Registry — Persistence -->
  <windows_registry>HKEY_LOCAL_MACHINE\Software\Microsoft\Windows\CurrentVersion\Run</windows_registry>
  <windows_registry>HKEY_CURRENT_USER\Software\Microsoft\Windows\CurrentVersion\Run</windows_registry>
  <windows_registry arch="both">HKEY_LOCAL_MACHINE\System\CurrentControlSet\Services</windows_registry>

  <!-- Registry — Advanced persistence (Winlogon, IFEO, AppInit) -->
  <windows_registry>HKEY_LOCAL_MACHINE\Software\Microsoft\Windows NT\CurrentVersion\Winlogon</windows_registry>
  <windows_registry>HKEY_LOCAL_MACHINE\Software\Microsoft\Windows NT\CurrentVersion\Image File Execution Options</windows_registry>
  <windows_registry>HKEY_LOCAL_MACHINE\Software\Microsoft\Windows NT\CurrentVersion\Windows</windows_registry>

  <!-- Registry — Defense evasion -->
  <windows_registry>HKEY_LOCAL_MACHINE\Software\Microsoft\Windows\CurrentVersion\Policies\System</windows_registry>
  <windows_registry>HKEY_LOCAL_MACHINE\Software\Policies\Microsoft\Windows Defender</windows_registry>

  <!-- Registry — LSA / Mimikatz protection -->
  <windows_registry>HKEY_LOCAL_MACHINE\System\CurrentControlSet\Control\Lsa</windows_registry>

  <!-- Registry — RDP -->
  <windows_registry>HKEY_LOCAL_MACHINE\System\CurrentControlSet\Control\Terminal Server</windows_registry>

  <!-- Ignore -->
  <ignore>C:\ProgramData\Microsoft\Windows Defender</ignore>
  <ignore>C:\Windows\System32\wbem\Logs</ignore>
  <ignore type="sregex">.tmp$|.log$|.etl$</ignore>

</syscheck>

Why These Registry Keys?

Registry KeyAttack Technique
CurrentVersion\Run / RunOnceBoot persistence — the most classic method
WinlogonShell hijacking — executing malware at logon
Image File Execution OptionsDebugger key abuse to run malware instead of the intended program
Windows (AppInit_DLLs)Loading a DLL into every process on startup
Policies\System (UAC)UAC bypass — defense evasion
Windows DefenderDisabling antivirus
Control\LsaMimikatz target — credential dumping
CurrentControlSet\ServicesNew service creation / rootkits
Terminal ServerRDP manipulation — lateral movement
⚡
A Critical Design Decision Machine-account logoff/logon events (4624/4634, accounts ending in $ like SRV201$) generate a lot of noise. They shouldn't be filtered out anyway. Machine-account logons can be a critical clue in detecting Pass-the-Hash and lateral movement. Once Shuffle and TheHive are in place, these should be filtered intelligently through correlation rules instead.
