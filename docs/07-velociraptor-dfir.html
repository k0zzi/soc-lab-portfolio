This post documents the seventh chapter of the SOC Lab build series. The previous six chapters set up detection (Suricata, Wazuh), response automation (Shuffle), and case management (TheHive + Cortex). This chapter adds a digital forensics (DFIR) layer to the stack: Velociraptor.

Every tool so far has been asking "did something happen?" Velociraptor answers a different question: "what actually happened on this endpoint?" When Wazuh generates an alert, Velociraptor can connect to that machine instantly and query a live, real-time picture — process list, network connections, prefetch, registry, event logs. It's the open-source equivalent of the "live response" feature found in commercial EDR products like CrowdStrike Falcon or Tanium.

ℹ
Prerequisite The Wazuh agents on SRV201, SRV202, and CLT601 from Chapter 3 need to be installed and deployed via the Sysmon GPO. This chapter adds the Velociraptor agent to the same three machines via GPO Software Installation — the same method used for the Sysmon rollout.
Architecture

Where Velociraptor Sits in the SOC Stack

Velociraptor is developed by Velocidex, part of Rapid7 — its founder, Mike Cohen, is an engineer who worked on digital forensics at Google. The tool is fully open source (AGPL) and isn't a hobby project: it's a reference tool in SANS Institute's DFIR curriculum (particularly FOR508 — Advanced Incident Response), and DFIR consultancies like Mandiant and KPMG use it in real operations.

It doesn't overlap with Wazuh — the two answer different questions. Wazuh is an always-on detection layer: logs get collected, rules match, alerts fire. Velociraptor is an on-demand investigation layer: once an alert comes in, you can ask "so what's actually on this machine?" live, using VQL (Velociraptor Query Language). Wazuh alerts become the trigger for a Velociraptor investigation.

🛡
A Defense-Sector Perspective Velociraptor runs entirely on-premise — forensic data never touches the cloud. That's the core reason cloud-dependent tools like CrowdStrike are unacceptable in some defense-sector environments. Open-source licensing is also an increasingly common preference in public-sector procurement for supply-chain security reasons — not because of budget constraints.

Step 01

Server Installation

Unlike the other tools, Velociraptor runs as a single binary — the same file acts as server, client, and admin CLI. No package manager, no dependencies, no repositories to add. It's the simplest install process in this lab. The official quickstart documentation (docs.velociraptor.app) was followed.

⚠
v0.76.5 — Not v0.76.6 v0.76.6 has a known bug in the debian server command (package generation fails). v0.76.5 was used for this lab.

⚠
Critical: bind_address Defaults to 127.0.0.1 By default, the wizard writes bind_address: 127.0.0.1 (loopback) for both Frontend and GUI — meaning only the VM itself can connect. Without fixing this, Windows agents can't reach the Frontend (8000), and the GUI (8889) can't be reached from a browser elsewhere either. 
server.config.yaml# Frontend section:
Frontend:
  bind_address: 0.0.0.0   # changed from 127.0.0.1

# GUI section:
GUI:
  bind_address: 0.0.0.0   # changed from 127.0.0.1

0.0.0.0 means "accept connections from every interface." Access control is already handled by OPNsense's firewall rules, so this isn't a security concern — if anything, it's more in line with defense-in-depth, since the control point sits at the network layer.

The core install ships with a few hundred artifacts, but additional sets produced by the community and Rapid7 Labs can be imported with one click from the GUI.

Run Server.Import.Extras

Step 04

Fleet Hunting — Baseline Forensic Sweep

Once the agent fleet was up, six baseline DFIR hunts were sent to the three endpoints (SRV201, SRV202, CLT601) in turn. Each hunt was launched by selecting the artifact from Hunt Manager → New Hunt and dispatching it to all 3 clients; once complete, results were queried with VQL in a Notebook.

1. Unsigned Process Sweep — Windows.System.Pslist

VQLSELECT Fqdn, Name, Exe, Authenticode.Trusted AS Trusted, Hash.SHA256 AS SHA256
FROM source(artifact="Windows.System.Pslist")
WHERE Authenticode.Trusted != "trusted" AND Exe != ""
ORDER BY Fqdn

Result: Clean. The only unsigned group that showed up was Proxmox's own VirtIO guest drivers (balloon, vioscsi, netkvm) — the virtualization layer's own drivers, expected and legitimate.

2. Network Connections — Windows.Network.Netstat (C2 Check)

VQLSELECT Pid, Name, Status, Laddr.IP, Laddr.Port, Raddr.IP, Raddr.Port
FROM source(artifact="Windows.Network.Netstat")
WHERE Status = "ESTABLISHED" AND Raddr.IP != "0.0.0.0"

Result: Clean. Every ESTABLISHED connection was accounted for — AD/DNS traffic (SRV201↔SRV202), Wazuh agent → Manager (10.1.30.10:1514), Velociraptor agent → Frontend (10.1.30.14:8000). No unexpected external IPs.

3. Persistence — Windows.Packs.Persistence

A sweep of WMI event subscriptions and the Startup folder. Result: Clean — no unauthorized WMI persistence or startup entries found.

4. Scheduled Tasks — Windows.System.TaskScheduler

Result: Clean. Every task was accounted for by GPO deployment scripts (Sysmon, Velociraptor) and Wazuh SCA's periodic check tasks.

5. Services — Windows.System.Services

VQL — whitelist approachSELECT ClientId, Name, DisplayName, State, StartMode, PathName, UserAccount
FROM source(artifact="Windows.System.Services")
WHERE PathName != ""
  AND NOT PathName =~ "(?i)(\\\\windows\\\\|program files|programdata\\\\microsoft|\\\\sysmon)"

A query for anything outside known-good path patterns (Windows, Program Files, Microsoft ProgramData, Sysmon). Result: Clean — the remaining services were the Velociraptor agent itself and previously known third-party software (the Proxmox guest agent, etc.).

6. Prefetch Analysis — Windows.Forensics.Prefetch

VQLSELECT ClientId, Executable, LastRunTimes, RunCount, PrefetchFileName
FROM source(artifact="Windows.Forensics.Prefetch")
WHERE Executable =~ "(?i)(powershell|cmd|wscript|cscript|mshta|rundll32|regsvr32|certutil|bitsadmin|net\.exe|whoami|mimikatz|psexec)"
ORDER BY ClientId
ℹ
Why Are All Results From CLT601? Prefetch is disabled by default on Windows server SKUs — that's why nothing came back from SRV201 or SRV202. CLT601 (Windows 11 Enterprise, a client SKU) keeps prefetch on; every result comes from there.

Tracking NET.EXE — Sysmon Event ID 1

NET.EXE's 37 executions were investigated further, since commands like net user and net group can be used for reconnaissance. Prefetch only answers "did it run?" — answering "when, by whom, with what arguments, called from which process?" requires Sysmon Event ID 1 (Process Creation).

"Prefetch only answers 'did it run?' Sysmon Event ID 1 answers 'when, by whom, with what arguments, called from which process?' — that's why it's the reference log source in IR playbooks and MITRE ATT&CK detections."

The Sysmon EID 1 review confirmed the NET.EXE executions came from periodic net user commands triggered by wazuh-agent.exe (the Wazuh SCA module's user/account policy checks). Result: accounted for, no threat.

Step 05

MITRE ATT&CK Hunt — Hayabusa

The hunts in Step 04 looked at specific artifact types. This step runs Windows.Hayabusa.Rules, scanning every Windows Event Log across the fleet against 4,850 Sigma-based MITRE ATT&CK rules — over 66,000 events processed.

VQL — summary, by unique titleSELECT Fqdn, Title, Level
FROM source(artifact="Windows.Hayabusa.Rules")
WHERE Fqdn =~ "SRV"
  AND Level != "informational"
  AND Level != "low"
GROUP BY Title, Fqdn, Level
ORDER BY Level DESC

Investigation 1 — AdFind.EXE Enumeration (False Positive)

Initial hypothesis: an attacker or tool might genuinely have run AdFind.exe. A direct search was run against Sysmon EID 1:

VQL — first attemptSELECT Fqdn, TimeCreated, EventData.Image AS Image,
       EventData.CommandLine AS CommandLine,
       EventData.ParentImage AS ParentImage,
       EventData.User AS User
FROM source(artifact="Windows.EventLogs.Evtx")
WHERE Channel = "Microsoft-Windows-Sysmon/Operational"
  AND EventID = 1
  AND EventData.Image =~ "(?i)adfind"
ORDER BY TimeCreated DESC

Result: table contains no data — no process named adfind.exe had ever run. So Hayabusa's own trigger detail was checked instead:

VQL — Hayabusa detailSELECT Fqdn, Timestamp, Title, Level, Channel, EID, Details
FROM source(artifact="Windows.Hayabusa.Rules")
WHERE Title =~ "AdFind"
ORDER BY Timestamp DESC

Mystery solved. Every alert traced back to the same actual command line:

The actual command — parent: wazuh-agent.exepowershell secedit /export /cfg $env:TEMP\secpol.cfg;
Get-Content $env:TEMP\secpol.cfg | Select-String "LockoutDuration";
Remove-Item $env:TEMP\secpol.cfg
✓
Result: False Positive This is the secedit /export command Wazuh's SCA (Security Configuration Assessment) module runs periodically to check the LockoutDuration policy. The Sigma rule mistakenly matched this command pattern to an AD-enumeration signature (an argument structure resembling AdFind). The parent process on every line is wazuh-agent.exe — not attacker activity.

Investigation 2 — Windows Defender Disabled (the Czech-Language Mystery)

The event message for the HIGH-severity "Windows Defender Real-time Protection Disabled" alert triggered by EID 5001 on SRV201 came back in Czech. Initial hypothesis: the system may have originally been installed with a Czech locale before being switched to Turkish — a leftover trace from the Windows Server ISO/template used for provisioning.

SRV201 — PowerShellGet-WinSystemLocale        # → Turkish
Get-WinUserLanguageList     # → only Turkish installed

The result was unexpected: the Czech language pack was found to have never been present — only Turkish was installed. The "used to be Czech, later removed" hypothesis was then tested via web research:

ℹ
Web Research Finding There's a documented bug — known since 2018 — in Windows Defender's MUI (Multilingual User Interface) resource files that causes event messages to show up in Czech or Polish regardless of the system's actual language. The same behavior has been reported on German systems too. SRV201's case matches this bug exactly: system locale is Turkish, only the Turkish language pack is installed, but the Defender message comes out in Czech.

The Turkish translation of the Czech message reads: "Real-time protection has disabled scanning for malware and other potentially unwanted software."

✓
Result: Accounted For The Defender-disabled event is real but was a one-off — tied to the lab setup process on June 1st (a temporary Defender exclusion during the Sysmon/Velociraptor agent installs). The Czech language wasn't the originally suspected "used to run a Czech locale" — it's a known Windows Defender MUI bug. No threat here; this investigation started as an "infer system history from event-log language" exercise and ended up identifying a product-specific MUI bug instead — a common turn of events in DFIR work.
