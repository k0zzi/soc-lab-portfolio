This post documents the sixth chapter of the SOC Lab build series. In earlier chapters, Suricata detected and dropped threats, Wazuh analyzed the logs, and Shuffle handled automatic IP blocking in OPNsense. This chapter adds two new layers: TheHive turns every detection into a case, and Cortex automatically queries and enriches the IPs in those cases with external data.

TheHive and Cortex complement each other but run on independent VMs. That separation is deliberate: independent snapshots, separate fault domains, and a structure closer to a production SOC architecture.

ℹ
Prerequisite Shuffle SOAR from Chapter 5 needs to be installed and the port-scan-auto-block workflow running. In this chapter, TheHive and Cortex are installed on separate VMs, and an observable-creation node is added to the Shuffle workflow to complete the chain.
Architecture

Where TheHive and Cortex Sit in the SOC Stack

TheHive is a SIRP (Security Incident Response Platform). It turns incoming alerts into cases, assigns tasks to analysts, and keeps a timeline. Cortex is the observable enrichment engine — it queries external sources about an IP, domain, or hash and writes the result back into the case.

Technically, enrichment could also be done through Wazuh's VirusTotal integration or a direct API call from Shuffle. Earlier in this lab, a VirusTotal integration was set up and tested through Wazuh. But that approach only shows a single analyst a log entry on their own screen — even if the event gets recorded, who investigated it, what action was taken, and where the process stands don't come together into something trackable and manageable.

In a real SOC, security events are handled by a team: one person does the initial triage, another runs the technical analysis, someone else reports up to a manager. TheHive makes that process manageable — every incident becomes a case, cases get assigned to analysts, every action taken lands on the timeline, and the whole team sees the same picture. Cortex enriches that picture further: by the time an analyst opens a case, data gathered from external sources about the IP is already sitting there waiting.

Step 01

Installing TheHive 5

TheHive was installed using StrangeBee's official automated install script. The script sets up Java, Cassandra or local storage, Elasticsearch, and TheHive itself in one pass.

ℹ
Why a Separate VM? TheHive and Cortex can run on the same server, but they were put on separate VMs in this lab. Each can take its own snapshot, and one going down doesn't affect the other. Production SOC architectures make this same separation.
1

VM Preparation

New VM in Proxmox: Ubuntu 24.04, 16 GB RAM, 80 GB disk, VLAN30, static IP 10.1.30.12.

2

The StrangeBee Automated Script

TheHive VM — 10.1.30.12wget -q -O /tmp/install-thehive.sh https://archives.strangebee.com/scripts/install-thehive.sh
sudo bash /tmp/install-thehive.sh

The script presented installation options. "Install TheHive only" was chosen for this lab — since Cortex lives on its own VM, the combined install wasn't needed.

3

First Login and Creating the Organization

Logged in at http://10.1.30.12:9000 with the default admin account. Platform Management → Organizations → new org: soc.dev

User Structure

Three users were created in TheHive, each with a deliberately separated role:

TheHive Users — Org: soc.dev
administrator@soc.devorg-admin · administrative tasks
zeynep.kocak@soc.devanalyst · case analysis
thehive-alert@soc.devService · analyst · Shuffle integration
ℹ
The Service Account Principle The Shuffle integration runs through the thehive-alert@soc.dev service account, not the admin account. Its account type is marked "Service" — a dedicated type for API access. The service account isn't in Active Directory — it stays local to TheHive.
⚠
Community License Limit TheHive's community license caps an organization at 2 regular users. Service accounts don't count against that limit. The trial Platinum license lasts 15 days; after that, it drops back to the community license.
Step 02

Installing Cortex 4

Cortex turned out to be more work than expected. StrangeBee's automated script misconfigures the Docker repository on Ubuntu 24.04, so the install failed. It was set up manually instead, following the official step-by-step documentation.

✕
StrangeBee Script Bug: Hardcoded Debian Instead of detecting the OS dynamically, the script hardcodes linux/debian when adding the Docker repository. The install failed on every version tried, including Ubuntu 24.04, Debian 13, and Ubuntu 20.04. The official step-by-step guide detects the OS correctly using the ${ID} variable.

1. Java Corretto 11

Cortex VM — 10.1.30.13wget -q -O - https://apt.corretto.aws/corretto.key | sudo gpg --dearmor \
  -o /usr/share/keyrings/corretto.gpg
echo "deb [signed-by=/usr/share/keyrings/corretto.gpg] \
  https://apt.corretto.aws stable main" | \
  sudo tee /etc/apt/sources.list.d/corretto.list
sudo apt update
sudo apt install -y java-11-amazon-corretto-jdk

2. Elasticsearch 8.x

Cortex VMwget -qO - https://artifacts.elastic.co/GPG-KEY-elasticsearch | \
  sudo gpg --dearmor -o /usr/share/keyrings/elasticsearch-keyring.gpg
echo "deb [signed-by=/usr/share/keyrings/elasticsearch-keyring.gpg] \
  https://artifacts.elastic.co/packages/8.x/apt stable main" | \
  sudo tee /etc/apt/sources.list.d/elastic-8.x.list
sudo apt update
sudo apt install -y elasticsearch
⚠
Critical for Elasticsearch 8.x: xpack.security Elasticsearch 8.x enables xpack.security automatically on install — SSL and authentication become mandatory. Cortex doesn't support that configuration. Without explicitly disabling three flags, Cortex can't connect to Elasticsearch at all. 
/etc/elasticsearch/elasticsearch.ymlxpack.security.enabled: false
xpack.security.http.ssl.enabled: false
xpack.security.transport.ssl.enabled: false

# Cluster setting required for Cortex
cluster.name: hive
http.host: 127.0.0.1

3. Docker

Cortex runs its analyzers as Docker containers. The ${ID} variable was used during setup — this avoids StrangeBee's hardcoded-Debian bug.

Cortex VMfor pkg in docker.io docker-doc docker-compose podman-docker containerd runc; do
  sudo apt-get remove -y $pkg 2>/dev/null
done

sudo apt-get install -y ca-certificates curl gnupg
sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/$(. /etc/os-release; echo "$ID")/gpg | \
  sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
sudo chmod a+r /etc/apt/keyrings/docker.gpg

echo "deb [arch=$(dpkg --print-architecture) \
  signed-by=/etc/apt/keyrings/docker.gpg] \
  https://download.docker.com/linux/$(. /etc/os-release; echo "$ID") \
  $(. /etc/os-release; echo "$VERSION_CODENAME") stable" | \
  sudo tee /etc/apt/sources.list.d/docker.list
sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io

4. cortexutils and the Cortex Package

Cortex VM# cortexutils — needs --break-system-packages on Ubuntu 24.04
sudo pip3 install cortexutils --break-system-packages

# Cortex DEB package
wget -qO - https://raw.githubusercontent.com/TheHive-Project/TheHive/master/PGP-PUBLIC-KEY | \

echo "deb [signed-by=/usr/share/keyrings/thehive-project.gpg] \
  https://deb.thehive-project.org release main" | \

5. Configuring Cortex

/etc/cortex/application.confsearch {
  uri = "http://127.0.0.1:9200"
}

# secret.key — generate with:
# cat /dev/urandom | tr -dc 'a-zA-Z0-9' | fold -w 64 | head -n 1
play.http.secret.key = "[generated-random-key]"

cache.job = 5 minutes
job {
  runner = [DockerJob, ProcessJob]
}
⚠
A Common secret.key Mistake The play.http.secret.key line was set to the path of the file holding the key, instead of the key value itself — Cortex wouldn't start. The value needs to go in directly as a string, not a file path.

Step 03

TheHive ↔ Cortex Integration

The connection between the two tools is configured from TheHive's Connectors interface. Cortex's API key is registered with TheHive, which lets TheHive query Cortex directly for observables.

1

Create an API Key in Cortex

http://10.1.30.13:9001 → log in as cortexanalyzer → top-right corner → API Key → generate and copy.

2

Add the Connector in TheHive

TheHive → Platform Management → Connectors → Cortex → Servers → +

Cortex Connector Settings
Server nameCortex-Lab
Server URLhttp://10.1.30.13:9001
API Keythe cortexanalyzer user's key
⚠
The Connection Disappears After a VM Restart TheHive keeps the Cortex connection in application state rather than writing it to a config file. When the VM restarts, the connection resets and has to be re-added from the connector page. This appeared to be a known TheHive 5 quirk at the time.

Update: the real root cause turned out to be a startup-ordering race condition — TheHive was coming up before its backend database was actually ready. A systemd override enforcing the correct startup order, combined with defining the connector in TheHive's own config file, gives this a permanent fix rather than needing to re-add it by hand after every restart.
Step 04

Analyzer Configuration

Cortex runs its analyzers as Docker containers. Two critical issues turned up after installation.

Issue 1: The Docker Group

The Cortex service runs as the cortex user. The Docker socket (/var/run/docker.sock) belongs to the docker group. Since the cortex user wasn't in that group, every analyzer failed with "Worker cannot be run."

Cortex VM# Diagnose the issue
id cortex
# Output: groups=1000(cortex),4(adm)... — no docker group

# Fix it
sudo usermod -aG docker cortex
sudo systemctl restart cortex
✓
The Docker Group Fix Is Critical No analyzer works at all without this change. The error message ("Worker cannot be run") doesn't point directly at a Docker access problem — diagnosing it means running id cortex and ls -la /var/run/docker.sock and checking the group membership by hand.

Issue 2: The Analyzer List Doesn't Show Up

Logging into Cortex as the global admin, the Analyzers tab appears empty. The analyzer list only shows up when logged in as the organization user (cortexanalyzer).

Active Analyzers

The following analyzers were enabled from the Organization → Analyzers tab, with free API keys entered:

AnalyzerSourceCoverageLimit
AbuseIPDB_2_0 abuseipdb.com IP reputation, report history, usage type, Tor flag 1,000 queries/day (free)
VirusTotal_GetReport_3_1 virustotal.com IP/domain history, resolution records, security-engine scan results 4 queries/min (free API)
ℹ
The VirusTotal Rate Limit The free VirusTotal API key is capped at 4 queries per minute. The VirusTotal integration set up earlier in Wazuh was disabled for this reason — enrichment is now managed centrally through Cortex instead of splitting the query budget across two places.
Step 05

Shuffle Integration: Automatic Observables

In Chapter 5, Shuffle's port-scan-auto-block workflow already opened a case in TheHive automatically. This chapter adds one more node to that workflow: once a case is created, the source IP gets added to it as an observable automatically.

Webhook → PortScanConfig → BLOCK branch
                                 ↓
                              block-ip (OPNsense)
                                 ↓
                         TheHive — Create Case ✓ Chapter 5
                                 ↓
              TheHive — Create Observable ✓ This chapter

The Create Observable Node

In Shuffle, the Create Observable in Case action was selected from the TheHive app.

Create Observable Node — Shuffle
ActionCreate Observable in Case
CaseId$thehive-api.body._id
Auththehive-alert@soc.dev API key
Observable Body{
  "data": "$exec.all_fields.data.src_ip",
  "dataType": "ip",
  "message": "Source IP - automated port scan",
  "tlp": 2,
  "ioc": true,
  "sighted": true,
  "tags": ["automated", "port-scan", "src-ip"]
}
ℹ
The Case ID Variable The response from the TheHive Create Case node includes a body._id field with the case's unique ID (e.g. ~16584). The Create Observable node picks that up via $thehive-api.body._id. If the node's name is different, the variable name needs to be updated to match.
