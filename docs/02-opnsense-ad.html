Architecture

What Was Built in This Chapter?

This post documents the second stage of building an actual SOC lab environment. Chapter 1 installed Proxmox and put the base virtualization infrastructure in place. This chapter adds two critical layers on top of it: the network was segmented along security-first principles using OPNsense, and Active Directory was set up on Windows Server to centralize user and device management.

This foundation had to be complete before moving on to Wazuh, Sysmon, and FIM in the next chapter. For Wazuh to collect meaningful logs, source devices needed to belong to a domain, and traffic from those devices needed to flow through a VLAN that could actually be monitored.

Step 01

Creating and Installing the OPNsense VM

OPNsense is an open-source, FreeBSD-based firewall and router distribution. It runs as a VM on Proxmox and was positioned as the single exit point for all network traffic.

Creating a Second Bridge (vmbr1) on Proxmox

OPNsense needed two legs: the existing vmbr0 for WAN, and a new vmbr1 for LAN (the internal network). Internet connectivity reaches OPNsense from the physical NIC via vmbr0; OPNsense then routes that traffic out to the internal network over vmbr1. This bridge wasn't connected to any physical port — it was configured purely as a virtual switch through which VMs communicate with each other.

1

Proxmox interface: Node → System → Network

From the left-hand menu, clicked the Proxmox node name (pve) and navigated to System → Network.

2

Create → Linux Bridge

Name: vmbr1 · IPv4/IPv6: left blank · Bridge ports: left blank · Comment: OPNsense-LAN. The VLAN-aware setting was configured in Step 02.

3

Apply Configuration

Clicked the Apply Configuration button at the top to apply the changes. Skipping this means the bridge won't be active until the next reboot.

OPNsense ISO and VM Creation

The OPNsense ISO was downloaded from opnsense.org/download. The amd64-dvd image was selected and uploaded to Proxmox's arch.srv (directory) storage.

💡
Recommended Hardware The OPNsense VM was given 2 vCPU · 8 GB RAM · 32 GB disk (SCSI). 8 GB of RAM is needed because Suricata IDS/IPS runs inside OPNsense; 1–2 GB would be enough for a firewall-only role.

While creating the VM, a second network card was added via Hardware → Add → Network Device and connected to vmbr1. This gave OPNsense its two-legged structure: vmbr0 (WAN) and vmbr1 (LAN leg).

Installation: Disk Preparation and the Installer

On first boot, the VM came up as OPNsense Live Media. Nothing done in this mode survives a reboot — the installation still had to be written to disk.

⚠️
Common Pitfall: Partition Destroy Failed Choosing ext4 as the filesystem during installation caused OPNsense to fail with this error. FreeBSD-based OPNsense doesn't support ext4 — switching the filesystem to UFS resolved it.

The installer was launched and Install (UFS) was selected. UFS was chosen over ZFS because ZFS's RAM overhead is unnecessary in this lab environment; UFS uses fewer resources and is sufficient for firewall/IDS workloads like OPNsense. Guided Disk Setup → disk selection → GPT → installation complete → Reboot. Before rebooting, the ISO was removed from the VM's Hardware tab — otherwise the system boots back into the installation media.

First Boot: Interface Assignment

On boot from disk, the console menu appeared. 1 (Assign Interfaces) was selected to assign the interfaces:

  • Should VLANs be set up now? → n (VLAN configuration would be done from the web interface)
  • WAN Interface: vmbr0 (the card connected to the modem)
  • LAN Interface: vmbr1 (the internal network card)
  • Confirmed: y

Next, 2 (Set Interface IP) was used to assign a static IP to LAN: 10.1.10.1/24. DHCP wasn't enabled from the console at this stage — DHCP for the VLANs was configured later from the web interface using Kea DHCP. Likewise, gateway definitions for each VLAN hadn't been created yet either — those were also set up individually, per VLAN interface, from the web interface.

✅
Connectivity Test From the console, 7 (Ping Host) was used to ping 8.8.8.8. A response came back at around 21 ms — the WAN connection was healthy. LAN connectivity couldn't be tested at this stage, since the VLANs hadn't been created yet and DHCP and gateways weren't configured. LAN verification happened once all of those steps were complete.
Step 02

VLAN Segmentation: Dividing the Network Into Secure Rooms

Running everything on a single flat network means that a single breach gives an attacker access to everything. VLAN segmentation removes that risk: each group of services sits in its own isolated VLAN, and all inter-VLAN traffic passes through — and is inspected by — OPNsense.

VLAN ID Name Purpose Subnet Gateway
VLAN 10 LAN OPNsense's LAN leg (10.1.10.5), web interface access 10.1.10.0/24 10.1.10.1
VLAN 20 Server (DMZ) SRV201 (DC + DNS), SRV202 (File Server) 10.1.20.0/24 10.1.20.1
VLAN 30 SOC Wazuh Manager (10.1.30.10), Shuffle SOAR (10.1.30.11) 10.1.30.0/24 10.1.30.1
VLAN 50 MGMT Central management VLAN — has access rights to every other VLAN 10.1.50.0/24 10.1.50.1
VLAN 60 Clients Windows clients, domain members 10.1.60.0/24 10.1.60.1
⚠
DHCP Should Only Be Active on VLAN 60 Every system in the table above — OPNsense, Wazuh, Shuffle, SRV201, SRV202 — is infrastructure and is configured with a static IP. Letting any of their IPs change would break firewall rules, Wazuh agent connections, and DNS records. DHCP should only be enabled on VLAN 60 (Clients), where end-user Windows machines can get dynamic IPs. DHCP must stay disabled on every other VLAN.

Creating VLANs in OPNsense

The OPNsense web interface was reached at https://10.1.10.5. The default password was changed on first login.

From the left-hand menu, Interfaces → Devices → VLAN was opened. Clicking the orange + button in the bottom-right applied the following configuration for each VLAN:

  • Parent Interface: vtnet1 — this is OPNsense's internal-network leg, corresponding to vmbr1 on the Proxmox side. vtnet0 is the WAN leg, where the internet reaches OPNsense.
  • VLAN Tag: 20, 30, 50, 60 — created individually for each
  • Description: descriptive names such as VLAN20_SERVER, VLAN30_SOC were used

Once all the VLANs were created, Interfaces → Assignments was opened. The Add button was clicked for each new vlanX on vtnet1 row. Each interface was then configured as follows:

ℹ
Don't Confuse VLAN with VXLAN VLAN (Virtual LAN) is the IEEE 802.1Q standard used to logically split a physical network — this is the method used in this lab. VXLAN, on the other hand, is an encapsulation protocol used to join networks across different physical locations over a tunnel — needed for scenarios like linking two Proxmox nodes together. For this lab, running on a single Proxmox host, VLAN is sufficient.
  • Enable Interface: checked
  • IPv4 Configuration Type: Static IPv4
  • IPv4 Address: 10.1.[VLAN_ID].1 / 24 (e.g. VLAN20 → 10.1.20.1)
  • Save → Apply Changes

Gateway Configuration

For each VLAN interface, System → Gateways → Configuration was opened. Clicking the orange + button in the bottom-right defined a gateway for each VLAN. Each VLAN's gateway is OPNsense's own IP on that VLAN:

VLANGateway IP
VLAN 2010.1.20.1
VLAN 3010.1.30.1
VLAN 5010.1.50.1
VLAN 6010.1.60.1
ℹ
Why Is a Gateway Needed? Without a gateway defined, a VLAN can't reach the internet. OPNsense creates a separate virtual interface for each VLAN, but that interface needs to know an "exit point" in order to route traffic to the internet or to other VLANs. The gateway is that exit point — on each VLAN, OPNsense's own IP (e.g. 10.1.30.1) is defined as the gateway. Without it, machines on a VLAN can only talk to each other and can't reach anything outside it.

DHCP was enabled only for VLAN 60. From the left-hand menu, Services → Kea DHCP → Kea DHCPv4 was selected. In the interface that opened, VLAN60 was selected under Interfaces. The IP range and the DNS nameserver to hand out were defined under the Subnets tab. DHCP was left disabled on every other VLAN, since all systems on those VLANs are configured with static IPs.

Proxmox Side: Making vmbr1 VLAN-Aware

In the Proxmox interface, Node → System → Network → vmbr1 was edited and the VLAN aware option was checked. VLAN tags won't work until this change is applied. After applying it, VMs could be assigned a VLAN tag.

A VLAN tag was assigned to each VM's network card as follows:

1

VM → Hardware → Network Device

Bridge: vmbr1 · VLAN Tag: the relevant VLAN ID · Model: VirtIO

2

Started the VM and checked its IP

For systems with a static IP, the IP was verified with ipconfig (Windows) or ip a. Client machines on VLAN 60 picked up an IP automatically via DHCP.

⚠
The Network Card Model Must Match Across All VMs During setup, using VirtIO on some VMs and E1000 or other models on others was observed to cause inter-VLAN communication issues. Differences in how various NIC models handle packets can occasionally cause unexpected communication breakdowns. Using the same model — preferably VirtIO — across all VMs is recommended.
Step 03

Firewall Rules: Who Goes Where

With the VLANs and gateways defined, the next step was to decide what each VLAN could reach. OPNsense evaluates rules top to bottom, and the first match wins. A block rule was placed at the bottom of every VLAN's rule set — everything above it defines what's allowed, and everything else is denied.

⚠
The LAN Default-Allow Rule Must Be Disabled OPNsense automatically adds a "Default allow LAN to any" rule to the LAN interface on install. As long as this rule is active, block rules written on the VLANs won't take effect — all traffic passes through this rule instead. VLAN isolation isn't possible until this rule, found under Firewall → Rules → LAN, is disabled.

The Rule-Writing Interface

Rules were written under Firewall → Rules → [VLAN_NAME]. in was selected as the Direction for every rule — in OPNsense, rules are written on the interface where the traffic arrives, and return traffic is automatically permitted by the stateful firewall. Protocol and port were chosen separately for each rule; OPNsense doesn't allow selecting TCP and UDP together in a single rule, so two separate rules were written for the same port where needed.

ℹ
Internet Access via !10.1.0.0/16 The HTTP/HTTPS rules use !10.1.0.0/16 as the destination. The exclamation mark means "except this range" — so ports 80/443 are open to everywhere except the entire internal network. This keeps internet access open while blocking general 443 access to interfaces on internal VLANs; which internal IPs can be reached is defined by explicit rules instead.
ℹ

Once all the rules were written, Apply Changes was applied. Basic connectivity tests were then run from each VLAN: internet access, DNS resolution, and whether VLAN isolation behaved as expected were all verified. Attempting to reach VLANs that shouldn't be reachable triggered the block rules as expected, while permitted services worked without issue.

Assigning a Static IP to SRV201

The Domain Controller's IP couldn't be allowed to change. To set a static IP, ncpa.cpl was typed into the Run dialog, the Ethernet adapter was selected from the network connections window that opened, and the following values were entered under Properties → Internet Protocol Version 4 (TCP/IPv4):

FieldValue

ℹ
Why 127.0.0.1 for DNS? SRV201 is also the authoritative DNS server for the domain, so it needs to point to itself for DNS — otherwise the AD installation wizard can't resolve the domain name and fails. This setting stays in place after installation too, since a DC should always check its own DNS first.

Installing Active Directory Domain Services

Server Manager was opened. The Active Directory Domain Services role was selected from the Add Roles and Features wizard and the installation completed. Once finished, the yellow warning icon that appeared in Server Manager was clicked, and Promote this server to a domain controller was selected.

Domain Controller Promotion

In the wizard that opened, Add a new forest was selected. soc.dev was entered as the domain name — not a real TLD, just a name used for the internal network. The forest and domain functional level were left at Windows Server 2016. The DNS Server option came pre-checked and was left as-is. A DSRM password was set and the wizard completed. The server rebooted automatically.

After the reboot, a login was performed as SOC\Administrator to confirm the domain setup had succeeded.

✅
DC Health Check Confirmed in Server Manager that the AD DS and DNS roles showed green. Checked Event Viewer for any installation errors. Verified in DNS Manager that DNS records for the soc.dev domain had been created.

Step 05

Users and Group Policy

An empty domain doesn't make for a meaningful test environment. User accounts and GPOs were created so Wazuh would have something close to realistic logs to work with. Everything here was done through Server Manager and its related admin tools.

Relaxing the Password Policy for the Test Environment

Before creating any users, the default password policy was relaxed to fit a test environment. The Group Policy Management Console (gpmc.msc) was opened and the Default Domain Policy was edited:

Under Computer Configuration → Policies → Windows Settings → Security Settings → Account Policies → Password Policy, the following settings were changed: Password must meet complexity requirements was set to Disabled, and Minimum password length was set to 1 character. Maximum password age was also set to 999 days, to avoid dealing with expiring passwords.

⚠
A Lab-Specific Choice These settings exist purely to make lab setup easier. Deliberately weak passwords were used so that Wazuh's password-policy violation alerts could be tested. None of this should ever be carried into a production environment.

OU Hierarchy

This project doesn't simulate different user groups or departmental structures — since Wazuh, Suricata, and the other tools built later would be configured to monitor every device regardless, there was no need for GPO targeting.

Creating Test Users

Two test users were created so that client machines on VLAN 60 could log into the domain. Active Directory Users and Computers (dsa.msc) was opened, and New → User was selected from the right-click menu on the Users container:

Group Policy

The Group Policy Management Console (gpmc.msc) was opened. Two GPOs were created via soc.dev → Group Policy Objects → New: a Sysmon Deployment GPO and a Wazuh Deployment GPO. These GPOs are covered in detail in the Wazuh installation chapter.

Advanced Audit Policy configuration for the Windows Event Log wasn't done at this stage. Those settings would be applied during Wazuh setup, once it was clear which logs needed to be collected.

Step 06

Client VM Setup and Domain Join

In this step, a Windows 11 client on VLAN 60 authenticated against the Domain Controller on VLAN 20. All traffic between the two VLANs passed through OPNsense's firewall rules.

Client VM: VLAN 60

Created a Windows 11 VM in Proxmox

Troubleshooting

Problems Hit During Setup

ProblemCauseFix
OPNsense install: "partition destroy failed" ext4 was selected as the filesystem UFS should be selected as the filesystem during OPNsense installation
Client not getting an IP from DHCP Wrong VLAN tag, or vmbr1 not VLAN-aware Checked and corrected the VM's VLAN tag and vmbr1's VLAN-aware setting
Ping between VLANs not working Missing OPNsense firewall rule Added a pass rule to the relevant VLAN tab, applied changes
GPO not applying Waiting on gpupdate Ran gpupdate /force

The rule was fixed via the Proxmox console. Without a snapshot, the VM might have had to be rebuilt
Communication issues between different NIC models Some VMs used VirtIO, others E1000 Standardized the NIC model to VirtIO across all VMs
⚠
Snapshots Taking a snapshot in Proxmox before every critical step makes it possible to roll back quickly if something goes wrong. This is especially useful before steps like firewall rule changes and domain promotion. Since every snapshot consumes disk space, how often they're taken and how many are kept should be planned around available disk capacity.
