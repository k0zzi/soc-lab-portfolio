# T1003.001 — OS Credential Dumping: LSASS Memory

**Tactic:** Credential Access (TA0006)
**Result:** 🛡️ **PREVENTED** — a different category from "missed": the technique never reached the SIEM/detection layer at all
**Test used:** [Atomic Red Team T1003.001, Test #2 — "Dump LSASS.exe Memory using comsvcs.dll"](https://github.com/redcanaryco/atomic-red-team/blob/master/atomics/T1003.001/T1003.001.md)

---

## Why this test

T1003.001 offers 14 predefined tests, most requiring a download (ProcDump, NanoDump, Mimikatz) or a Python package install. Test #2 (`rundll32.exe comsvcs.dll, MiniDump`) needs neither — it uses only a built-in Windows DLL.

Three sources confirm this is a mainstream, actively-relevant technique rather than a niche choice:

1. **MITRE's own official T1003.001 technique page** lists this exact command as its named example: *"Built-in Windows tools such as comsvcs.dll can also be used: `rundll32.exe C:\Windows\System32\comsvcs.dll MiniDump PID lsass.dmp full`."*
2. The canonical SigmaHQ detection rule for this technique (`proc_access_win_lsass_dump_comsvcs_dll`) was authored by **Roberto Rodriguez (Cyb3rWard0g)** — the same recognized threat-hunting researcher (HELK/OTRF founder) cited in the T1218 finding for the UWP/DCOM activation pattern.
3. **Elastic maintains an official prebuilt rule** specifically for a renamed-`comsvcs.dll` variant of this technique — confirming it is treated as a mainstream, actively-monitored technique, not an obscure one.

## Execution — attempt 1: Defender active

```powershell
Invoke-AtomicTest T1003.001 -TestNumbers 2
```

Failed immediately with *"Erişim engellendi"* and a Windows Security threat notification: Defender identified it as **`Trojan:Win32/RundllLolBin.AF`**, severity 5 (high). No `comsvcs.dll` process-creation event appeared in Sysmon at all — Defender intervened at process-creation time, before Sysmon could even log the attempt.

## Execution — attempt 2: Defender disabled, technique still failed

Windows Security's Tamper Protection blocked `Set-MpPreference -DisableRealtimeMonitoring $true` from PowerShell — this is expected, documented Microsoft behavior (disabling Defender programmatically is itself something the product is designed to resist). Defender was disabled manually via the Windows Security GUI instead.

Re-running the test with Defender off: **exit code 0, but no dump file was ever created** (`Test-Path "$env:TEMP\lsass-comsvcs.dmp"` → `False`). No `comsvcs.dll` Sysmon event appeared in this run either.

Root cause: **`RunAsPPL: 2`** (LSASS configured as a UEFI-locked Protected Process Light) was active on CLT601. Windows' kernel blocks any non-PPL process from acquiring the access rights needed to read LSASS memory — independent of whether Defender is running at all.

## Two independent, layered prevention mechanisms

| Layer | Mechanism | Scope |
|---|---|---|
| EDR/AV | Windows Defender real-time protection, signature `Trojan:Win32/RundllLolBin.AF` | Blocks at process level |
| OS/kernel | `RunAsPPL: 2` (UEFI-locked PPL) | Blocks at memory-access level, regardless of AV state |

Either layer alone would have prevented the technique; together they are genuine defense-in-depth, and the Defender signature name confirms this specific technique (comsvcs+MiniDump+LSASS) is a named, signature-level-recognized threat, not a novel evasion this lab happened to catch by luck.

## Why "Wazuh coverage" is unanswerable here — a principled limit, not a gap

`RunAsPPL` prevents the technique from ever touching LSASS, so no Sysmon Event 10 (`ProcessAccess`) or dump-file event can be generated for Wazuh to process at all — not because Wazuh lacks a rule, but because the precondition for any such event never occurs. Asking "would Wazuh have caught this" is not a meaningful question under this configuration.

## Sourcing for the RunAsPPL configuration

- **CIS Benchmark for Windows Server** — the control *"Ensure 'Configures LSASS to run as a protected process' is set to 'Enabled: Enabled with UEFI Lock'"* appears across multiple current CIS Windows Server benchmark editions (its exact control number varies slightly by edition — e.g. 18.9.27.2 in the Server 2022 v5.0.0 Domain Controller benchmark, 18.9.27.1 in the Server 2022 v2.0.0 Stand-alone benchmark — but the setting and its recommended value are consistent across all of them). This maps to **NIST 800-53 SI-16** (Memory Protection) and matches CLT601's `RunAsPPL: 2` exactly.
- **MITRE ATT&CK's official mitigation M1025** (Privileged Process Integrity): *"Enable RunAsPPL on Windows systems to protect LSASS and other critical processes."*
- **Microsoft's own product decision**: PPL is enabled by default on new Windows 11 22H2 installations — this is the OS vendor's own baseline, not merely a third-party hardening recommendation.

Combined: the lab's `RunAsPPL: 2` (UEFI Lock) configuration is consistent with the CIS Benchmark control above, NIST 800-53 SI-16, and MITRE's own M1025 mitigation — three independent institutional sources agreeing on the same control.

## An acknowledged limitation of RunAsPPL

RunAsPPL is not a silver bullet. SysReptor and Clément Labro's 2021 OSSIR presentation (Labro received Microsoft's MSRC 2020 Most Valuable Security Researcher recognition) both document the known bypass path: **BYOVD** (Bring Your Own Vulnerable Driver). An attacker able to load a signed-but-vulnerable kernel driver can strip the PPL flag from the `lsass.exe` process object in kernel memory — a significantly more advanced, higher-privilege attack path than the standard `comsvcs.dll` technique, and one where AV/EDR products have detection opportunities at the driver-loading stage itself. Noting this limitation is part of accurate documentation here: RunAsPPL eliminates the easy, Atomic-test-level path entirely, but is not an absolute guarantee against a more capable adversary.

## Follow-up: even without RunAsPPL, the existing Sysmon rule would have missed this specific technique

Investigated separately: would this lab have had *any* detection opportunity for the comsvcs.dll technique if RunAsPPL were absent? Direct inspection of the live Sysmon config file (`C:\Windows\sysmonconfig.xml`) showed the ProcessAccess (Event 10) include rule only matches `CallTrace contains dbghelp.dll` or `dbgcore.dll`. The `comsvcs.dll` MiniDump technique does not route through either DLL, so it would not have matched this rule regardless of RunAsPPL.

This is a known, named coverage gap, not a misconfiguration — confirmed via Elastic's own official rule structure. Elastic's production rule **"Potential Credential Access via LSASS Memory Dump"** is explicitly scoped to `dbghelp`/`dbgcore` only. Elastic maintains a **separate, second** official rule — **"Potential Credential Access via Renamed COM+ Services DLL"** (production, created 2021, updated 2025) — specifically because the first rule cannot catch `comsvcs.dll`: *"Identifies suspicious renamed COMSVCS.DLL Image Load... may indicate an attempt to dump LSASS memory while bypassing command-line based detection."* This second rule requires Sysmon **ImageLoad (Event 7)** logging for `comsvcs.dll` — a different data source than this lab's existing ProcessAccess rule covers, and one not currently enabled.

Full coverage matching Elastic's own two-rule production approach requires three independent layers:

| Layer | Data source | Status in this lab |
|---|---|---|
| ProcessAccess / `CallTrace: dbghelp`, `dbgcore` | Sysmon Event 10 | ✅ Present |
| ImageLoad / `comsvcs.dll` specifically | Sysmon Event 7 | ❌ Not present — a third, distinct Sysmon config gap alongside the T1218 and T1055 findings |
| ProcessCreate / `rundll32.exe` + `comsvcs.dll` + `MiniDump` commandline | Sysmon Event 1 | Present in Sysmon's general include list, though never verified end-to-end against a Wazuh rule |

This is queued as a third documented Sysmon-config gap, to be addressed in the same batched remediation pass as the T1218 and T1055 findings (see the [T1218 finding](./T1218.md) for the NIST SP 800-115 rationale for deferring it).

## Result summary

**Prevented, not missed.** Defense-in-depth (Windows Defender + RunAsPPL) worked as designed, consistent with CIS/NIST/MITRE institutional guidance, and stopped the technique before it could reach any layer this lab's SIEM could observe. A follow-up investigation additionally confirmed that, independent of prevention, the existing Sysmon ProcessAccess rule would not have caught this specific DLL variant of the technique regardless.
