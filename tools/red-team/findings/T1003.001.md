# T1003.001 — OS Credential Dumping: LSASS Memory

**Tactic:** Credential Access (TA0006)
**Result:** 🛡️ **PREVENTED** — a different category from "missed": the technique never reached the SIEM/detection layer at all
**Test used:** [Atomic Red Team T1003.001, Test #2 — "Dump LSASS.exe Memory using comsvcs.dll"](https://github.com/redcanaryco/atomic-red-team/blob/master/atomics/T1003.001/T1003.001.md)

---

## Why this test

T1003.001 offers 14 predefined tests, most requiring a download (ProcDump, NanoDump, Mimikatz) or a Python package install. Test #2 (`rundll32.exe comsvcs.dll, MiniDump`) needs neither — it uses only a built-in Windows DLL.

Three sources confirm this is a mainstream, actively-relevant technique rather than a niche choice:

1. **MITRE's own official T1003.001 technique page** lists this exact command as its named example: *"Built-in Windows tools such as comsvcs.dll can also be used: `rundll32.exe C:\Windows\System32\comsvcs.dll MiniDump PID lsass.dmp full`."*
2. The canonical SigmaHQ detection rule for this technique (`proc_access_win_lsass_dump_comsvcs_dll`) was authored by **Roberto Rodriguez (Cyb3rWard0g)** — the same recognized threat-hunting researcher (HELK/OTRF founder) cited in the T1218 finding for the UWP/DCOM activation pattern.
3. **Elastic maintains an official prebuilt rule** specifically for a renamed-`comsvcs.dll` variant of this technique — confirming it is treated as a mainstream, actively-monitored technique, not an obscure one.

## Execution — attempt 1: Defender active

```
Invoke-AtomicTest T1003.001 -TestNumbers 2
```

Failed immediately with *"Erişim engellendi"* and a Windows Security threat notification: Defender identified it as **`Trojan:Win32/RundllLolBin.AF`**, severity Severe. No `comsvcs.dll` process-creation event appeared in Sysmon at all — Defender intervened at process-creation time, before Sysmon could even log the attempt.

## Execution — attempt 2: Defender disabled, technique still failed

Windows Security's Tamper Protection blocked `Set-MpPreference -DisableRealtimeMonitoring $true` from PowerShell — this is expected, documented Microsoft behavior (disabling Defender programmatically is itself something the product is designed to resist). Defender was disabled manually via the Windows Security GUI instead.

Re-running the test with Defender off: **exit code 0, but no dump file was ever created** (`Test-Path "$env:TEMP\lsass-comsvcs.dmp"` → `False`). No `comsvcs.dll` Sysmon event appeared in this run either.

Root cause: **`RunAsPPL: 2`** (LSASS configured to run as a Protected Process Light, without a UEFI lock) was active on CLT601. Windows' kernel blocks any non-PPL process from acquiring the access rights needed to read LSASS memory — independent of whether Defender is running at all.

## Two independent, layered prevention mechanisms

| Layer     | Mechanism                                                                       | Scope                                                 |
| --------- | ------------------------------------------------------------------------------- | ----------------------------------------------------- |
| EDR/AV    | Windows Defender real-time protection, signature `Trojan:Win32/RundllLolBin.AF` | Blocks at process level                               |
| OS/kernel | `RunAsPPL: 2` (PPL, no UEFI lock)                                                 | Blocks at memory-access level, regardless of AV state |

Either layer alone would have prevented the technique; together they are genuine defense-in-depth, and the Defender signature name confirms this specific technique (comsvcs+MiniDump+LSASS) is a named, signature-level-recognized threat, not a novel evasion this lab happened to catch by luck.

## Why "Wazuh coverage" is unanswerable here — a principled limit, not a gap

`RunAsPPL` prevents the technique from ever touching LSASS *memory*, so no Sysmon Event 10 (`ProcessAccess`) carrying the access rights a credential-dump would need can be generated for Wazuh to process — not because Wazuh lacks a rule, but because the precondition for any such event never occurs. (This is refined below: `RunAsPPL` blocks the memory-access step specifically, not the earlier `comsvcs.dll` module-load step — see the Update section.)

## Sourcing for the RunAsPPL configuration

- **CIS Benchmark for Windows Server** — the control *"Ensure 'Configures LSASS to run as a protected process' is set to 'Enabled: Enabled with UEFI Lock'"* appears across multiple current CIS Windows Server benchmark editions (its exact control number varies slightly by edition — e.g. 18.9.27.2 in the Server 2022 v5.0.0 Domain Controller benchmark, 18.9.27.1 in the Server 2022 v2.0.0 Stand-alone benchmark — but the setting and its recommended value are consistent across all of them). This maps to **NIST 800-53 SI-16** (Memory Protection) CIS recommends the UEFI-lock variant (`RunAsPPL` = 1), whereas CLT601 uses value 2 (enabled without a UEFI lock), so it matches the control's intent but not its exact recommended value.
- **MITRE ATT&CK's official mitigation M1025** (Privileged Process Integrity): *"Enable RunAsPPL on Windows systems to protect LSASS and other critical processes."*
- **Microsoft's own product decision**: Microsoft Learn documents that added LSA protection is enabled by default on new (not upgraded) Windows 11 22H2-and-later installations that are enterprise-joined and HVCI-capable, and that this automatic enablement does not set a UEFI variable — the OS vendor's own baseline, not merely a third-party hardening recommendation.

Combined: the lab's `RunAsPPL: 2` configuration follows the intent of the CIS Benchmark control above (which recommends the UEFI-lock variant), NIST 800-53 SI-16, and MITRE's own M1025 mitigation — three independent institutional sources agreeing on the same control: run LSASS as a protected process.

## An acknowledged limitation of RunAsPPL

RunAsPPL is not a silver bullet. SysReptor and Clément Labro's 2021 OSSIR presentation (Labro received Microsoft's MSRC 2020 Most Valuable Security Researcher recognition) both document the known bypass path: **BYOVD** (Bring Your Own Vulnerable Driver). An attacker able to load a signed-but-vulnerable kernel driver can strip the PPL flag from the `lsass.exe` process object in kernel memory — a significantly more advanced, higher-privilege attack path than the standard `comsvcs.dll` technique, and one where AV/EDR products have detection opportunities at the driver-loading stage itself. Noting this limitation is part of accurate documentation here: RunAsPPL eliminates the easy, Atomic-test-level path entirely, but is not an absolute guarantee against a more capable adversary. Because value 2 is stored only in the registry (no UEFI variable), an administrator can also turn it off by changing that value and rebooting; Microsoft's documentation describes the UEFI-lock variant as the one that cannot be changed through the registry or policy.

## Follow-up, corrected: the existing Sysmon config already has an ImageLoad rule for comsvcs.dll

Investigated separately: would this lab have had *any* detection opportunity for the comsvcs.dll technique if RunAsPPL were absent? Direct inspection of the live Sysmon config file (`C:\Windows\sysmonconfig.xml`) showed the ProcessAccess (Event 10) include rule only matches `CallTrace contains dbghelp.dll` or `dbgcore.dll`. The `comsvcs.dll` MiniDump technique does not route through either DLL, so it would not have matched this rule regardless of RunAsPPL.

This is a known, named coverage gap for the ProcessAccess rule specifically, not a misconfiguration — confirmed via Elastic's own official rule structure. Elastic's production rule **"Potential Credential Access via LSASS Memory Dump"** is explicitly scoped to `dbghelp`/`dbgcore` only. Elastic maintains a **separate, second** official rule — **"Potential Credential Access via Renamed COM+ Services DLL"** (production, created 2021, updated 2025) — specifically because the first rule cannot catch `comsvcs.dll`: *"Identifies suspicious renamed COMSVCS.DLL Image Load... may indicate an attempt to dump LSASS memory while bypassing command-line based detection."*

**A later remediation session corrected an error in this document's original conclusion.** The original text below (now struck through in substance, corrected here) claimed Sysmon Event 7 (ImageLoad) coverage for `comsvcs.dll` was "not present — a third, distinct Sysmon config gap." A full `sysmon64.exe -c` dump of the live Balanced config, read directly rather than assumed, showed this was incorrect: the ImageLoad include list already contains **Compound Rule 0096** — `Image ends with 'rundll32.exe' AND OriginalFileName is 'comsvcs.dll'` — matching exactly this technique. This rule has been present in this environment's Balanced config from the start; its existence was simply missed in the original investigation. The corrected coverage table:

| Layer                                                                   | Data source     | Status in this lab                                               |
| ------------------------------------------------------------------------ | --------------- | ------------------------------------------------------------------ |
| ProcessAccess / `CallTrace: dbghelp`, `dbgcore`                          | Sysmon Event 10 | ✅ Present, but does not match this technique's actual API path    |
| ImageLoad / `Image: rundll32.exe` + `OriginalFileName: comsvcs.dll`      | Sysmon Event 7  | ✅ Present (Compound Rule 0096) — previously misreported as absent |
| ProcessCreate / `rundll32.exe` + `comsvcs.dll` + `MiniDump` commandline | Sysmon Event 1  | Present in Sysmon's general include list                          |

## Update — Event 7 and Event 10 retest, with Defender disabled

A later remediation session retested specifically to answer the question this document originally left open: does Compound Rule 0096 actually fire under the exact condition of this test (Defender disabled, `RunAsPPL` still active)?

**Event 7 (ImageLoad) — fired, reached Wazuh, but produced no alert.** Two independent test runs both confirmed `comsvcs.dll` ImageLoad events reaching `archives.json`. This confirms Compound Rule 0096 works as designed at the Sysmon level. However, no Wazuh rule inspects `imageLoaded` content for `comsvcs.dll` specifically — the data reaches the SIEM and is silently unused. This is a genuine Wazuh ruleset gap, distinct from a Sysmon config gap: the telemetry exists, nothing looks at it.

**Event 10 (ProcessAccess, lsass.exe target) — never fired, and this is now understood architecturally, not just empirically.** MITRE's own DET0363 ("Detection of Credential Dumping from LSASS Memory via Access and Dump Sequence," analytic AN1030, Oct 2025) specifies the detection precondition precisely: *"a non-privileged or abnormal process attempts to open a handle with full access (0x1F0FFF) to lsass.exe."* `RunAsPPL` blocks exactly this step — the `OpenProcess` call needed to acquire that handle — at the kernel level, before Sysmon's ProcessAccess hook can ever fire. DET0363's own primary data source (Process Access, Sysmon EventCode=10) is therefore structurally incompatible with an environment where `RunAsPPL` is enforced: the strategy assumes a handle can be opened and then inspected, but `RunAsPPL` prevents the handle from being opened at all. This is not a rule-tuning problem; it is a precondition mismatch between the detection strategy and this environment's OS-level mitigation.

### Two further Sysmon config mistagging defects, found while confirming the above

Neither is a Wazuh ruleset issue — both concern the Sysmon config's own `RuleName`/`technique_id` annotations, which come from upstream and were left uncorrected as they sit outside this project's local rule files:

- The `comsvcs.dll` Event 7 record's own `RuleName` field reads `technique_id=T1003.004,technique_name=LSASS Memory` — the ID and the name disagree: T1003.004 is LSA Secrets, while LSASS Memory is T1003.001 (confirmed in the archived Event 7 records, all with this exact `RuleName`).
- The Event 1 (ProcessCreate) records that mention both `rundll32` and `comsvcs` carry several different `RuleName` values in the archive: `technique_id=T1083,technique_name=File and Directory Discovery` (6 records), `technique_id=T1218.011,technique_name=rundll32.exe` (3), `technique_id=T1059.003,technique_name=Windows Command Shell` (4) and `technique_id=T1059.001,technique_name=PowerShell` (1). The T1083 tag is the most frequent and is unrelated to credential access; the T1218.011 tag fits the rundll32 activity.

## Update — Wazuh rule 100240 closes the Event 7 ruleset gap

A later remediation session closed the Wazuh ruleset gap this document identified above (Event 7 telemetry reaching Wazuh with no rule inspecting it). Rule 100240 (`if_group: sysmon_event7`, matching `win.eventdata.image` ending in `rundll32.exe` AND `win.eventdata.originalFileName` equal to `comsvcs.dll`) was deployed and verified live: fires reliably (level 14, `mail:true`, `mitre: T1003.001`) on the exact reproduction steps used in this test, with no false positives observed in the test runs (the environment archives had been rotated, so no historical Event 7 baseline exists to check against).

Two institutional sources confirm Event 7 (ImageLoad) is a recognized, standard detection opportunity for this exact technique, independent of this project's own reasoning: Red Canary's own Threat Detection Report names Sysmon Event 7 as a valid collection point for the comsvcs.dll/MiniDump pattern, and a second industry write-up (Hawk-Eye) lists the same. Notably, Elastic's own production rule for this DLL only targets the *renamed* variant (`not file.name : "COMSVCS.DLL"`) — Compound Rule 0096's `OriginalFileName`-based approach, and by extension rule 100240, is broader than Elastic's own coverage, catching both renamed and plain usage.

This means the comsvcs.dll+rundll32 *attempt* is now detected at the Wazuh layer regardless of whether `RunAsPPL` subsequently blocks the memory-access step — a genuine, if narrow, improvement in this lab's visibility into this technique, independent of the prevention outcome documented above.

## Command-line detection (rule 100250)

Rule 100250 (level 12, T1003.001) inspects Sysmon Event 1 command lines for `rundll32` + `comsvcs` + `full` combined with `MiniDump` or an ordinal form (`#-`, `#+`, `#24`, `#65560`), or, without `rundll32`, `24` + `comsvcs` + `full` + a `#` form. It is ported from SigmaHQ's `proc_creation_win_rundll32_process_dump_via_comsvcs.yml` (id 646ea171; upstream revision of 2025-02-23) and is independent of rule 100240, which watches the module load (Event 7). MITRE's DET0363 lists Sysmon Event 1 as a log source and a `CommandLinePattern` element that names `comsvcs.dll` among common dump syntaxes, so the rule matches a data source and a pattern that strategy itself names. Two deviations from the Sigma original: the image/OriginalFileName condition is replaced by the string `rundll32` in the command line, and Sigma's T1036 tag is not carried over because renamed-binary detection is not implemented.

Validation:

- Historical data: the pattern matched all four archived `comsvcs.dll ... MiniDump ... full` command lines and no other command line among 3,101 archived Event 1 records (checked with PCRE outside Wazuh).
- Live, with Defender real-time protection and Tamper Protection temporarily disabled: Atomic Test #2 and three manual runs (`MiniDump`, `,#24`, `,#65560`) all fired 100250 (level 12, mail: true, T1003.001). Each run produces two alerts, one for the wrapping shell (`cmd.exe` or `powershell.exe`, whose command line carries the same tokens) and one for `rundll32.exe`, the same behavior as the Sigma original.
- Negative controls, both delivered to Wazuh as Event 1 and neither firing 100250: a command line with `rundll32`, `comsvcs` and `MiniDump` but no `full`, and one with `rundll32 24 full` but no `comsvcs` (both `echo` commands, not real rundll32 executions).
- Not tested: the `#-` and `#+` ordinal forms and Sigma's generic branch (command lines without `rundll32`).

Limitation: with Defender active, Atomic Test #2 is blocked before the process is created (Trojan:Win32/RundllLolBin.AF, access denied at process start), so no Event 1 exists and this rule cannot fire in that configuration. With Defender off, RunAsPPL still blocks access to LSASS memory (see above). The rule is a second detection point for when the prevention layer is disabled or bypassed, not a replacement for it.

## Result summary

**Prevented, not missed**, and the coverage picture is more complete than originally documented. Defense-in-depth (Windows Defender + RunAsPPL) worked as designed, consistent with CIS/NIST/MITRE institutional guidance, and stopped the technique's memory-access step before it could reach any layer this lab's SIEM could observe. The ImageLoad layer (Sysmon Event 7, Compound Rule 0096) does exist and does fire — the earlier claim that it was absent was incorrect. The resulting Wazuh ruleset gap (no rule inspecting this telemetry) has since been closed via rule 100240 — see the Update section above. Separately, DET0363's Event 10/AccessMask strategy is architecturally incompatible with this environment's `RunAsPPL` enforcement, independent of any rule that could be written. A command-line rule (100250, above) adds a further Wazuh detection point that fires only when the prevention layer is disabled or bypassed.
