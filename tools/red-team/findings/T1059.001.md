# T1059.001 — Command and Scripting Interpreter: PowerShell

**Tactic:** Execution (TA0002)
**Result:** ✅ **CAUGHT** — plus one sourced ruleset defect found and fixed along the way
**Test used:** [Atomic Red Team T1059.001, Test #17 — "PowerShell Command Execution"](https://github.com/redcanaryco/atomic-red-team/blob/master/atomics/T1059.001/T1059.001.md)

---

## Why this test

Twenty-two Atomic tests exist under T1059.001. Test #17 was selected over the alternatives on four criteria:

- **Zero dependencies** — no `Install-Module`, no external payload download (unlike #1–4, #13–16).
- **A "pure" T1059.001 test** — no bleed into another technique (unlike #10/#11, which are really T1027/T1112/T1564.004; or #20, which mixes in T1071.004-style DNS abuse).
- **Genuine execution, not simulation** — it actually runs a real encoded PowerShell command, unlike #18, which only prints "pretending to invoke" without executing anything.
- **Authoritative sourcing** — cited from Red Canary's own 2021 Threat Detection Report, not an arbitrary practitioner blog.

The command uses `-EncodedCommand` (base64) — a real, minimal evasion technique against naive string-matching detections. This makes it a meaningful test of whether Sysmon/Wazuh actually decode and inspect obfuscated command content, not just plaintext strings.

```
powershell.exe -e <base64>
```
which decodes to a simple `Write-Host "Hello, from PowerShell!"` payload.

## Execution

Run on CLT601 via Invoke-AtomicRedTeam:

```powershell
Invoke-AtomicTest T1059.001 -TestNumbers 17
```

## Result

Wazuh's default ruleset caught it correctly and at high severity:

**Rule 92057** — *"Powershell.exe spawned a powershell process which executed a base64 encoded command"*
`level: 12`, `mail: true`, `mitre: T1059.001 / Execution`

Read the rule's own XML to confirm the tag was earned, not just present: the field logic genuinely inspects `win.eventdata.commandLine` for `-e`/`-encodedcommand` variants — this is real content inspection, not a name-only match. **T1059.001: caught, correctly labeled, high severity** — overturning this project's own initial prediction (based on general LOLBin/discovery techniques usually being the ones missed) that this technique would slip through.

## Bonus finding — rule 92032 mistagging

The same test chain also fired **rule 92032** ("Suspicious Windows cmd shell execution", `level: 3`) in Wazuh's bundled default ruleset (`0800-sysmon_id_1.xml`) — not a local/custom rule.

Reading its actual XML logic:

```xml
<if_sid>92031, 61603</if_sid>
<field name="win.eventdata.parentImage" type="pcre2">(?i)cmd\.EXE</field>
<field name="win.eventdata.parentCommandLine" type="pcre2">(?i)\s\/C\s</field>
```

statically tagged, regardless of match path:

```xml
<mitre>
  <id>T1087</id>
  <id>T1059.003</id>
</mitre>
```

The problem: `if_sid` allows the rule to fire through **two independent parent paths**. Rule `92031` (matches `net.exe`/`net1.exe` by `OriginalFileName`) is genuine, evidence-based T1087 (Account Discovery) coverage. But `61603` is an **unconditional catch-all** — Wazuh's base "Sysmon Event 1: process creation" rule, level 0, with no field conditions at all, firing on *every single process creation event*. The captured T1059.001 test event had zero `net.exe` involvement and reached 92032 purely through the `61603` path — meaning the T1087/T1059.003 tags were applied with **no discovery-related evidence whatsoever** in that specific firing.

### Sourcing — is this a known problem class, or a one-off?

Confirmed via two authoritative primary sources, not blog opinion:

1. **[CISA + MITRE ATT&CK, "Best Practices for MITRE ATT&CK® Mapping"](https://www.cisa.gov/resources-tools/resources/best-practices-mitre-attckr-mapping) (v2.0, January 2023, TLP:CLEAR, co-authored with DHS-owned FFRDC HSSEDI).** Names this exact failure mode **"Leaping to Conclusions"** — *"prematurely deciding on a mapping based on insufficient evidence... e.g., incorrectly mapping malware using ports 80/443 to T1071.001 without first confirming usage of the HTTP/S protocol."* States explicitly: *"If there is insufficient detail to identify an applicable technique, analysts will be limited to mapping to the tactic level... Only limit mapping to the tactic level when there is insufficient detail to identify an applicable technique or sub-technique."*
2. **Elastic's own official documentation** confirms a directly comparable rule — "PowerShell spawning Cmd" (`process.parent.name: powershell.exe AND process.name: cmd.exe`, the reverse parent/child direction of 92032, but the same underlying defect class: a bare name-only match, tagged to the exact T1059.001 sub-technique, with no command-line content inspection) — was formally **deprecated on 2021/04/15** at `severity: low` / `risk_score: 21`. An independent major vendor reached the same conclusion for the same class of rule: a bare parent/child pattern match, with no content inspection, is not sound as a standalone, specifically-tagged detection.

### Verified: removing the tags costs zero real coverage

Dedicated, evidence-based `net.exe` discovery coverage already exists independently of 92032 and is unaffected by this fix:

- Rule `92031` itself (evidence-based, `OriginalFileName: net.exe/net1.exe`)
- Rule `92033` (`net.exe` spawned via PowerShell → T1087+T1059.001, evidence-based)
- Three further unnamed rules in the same file describing *"net.exe domain discovery command"*, *"net.exe account discovery command"*, and *"net.exe connection to a remote resource"*

## Fix applied

Local override in `local_rules.xml`, `overwrite="yes"`, same rule ID, placed in a new `ruleset_corrections` group (kept separate from the project's existing MISP-correlation local rules — this group is reserved specifically for correcting default-ruleset defects):

### Before (Wazuh bundled default, `0800-sysmon_id_1.xml`)

```xml
<rule id="92032" level="3">
  <if_sid>92031, 61603</if_sid>
  <field name="win.eventdata.parentImage" type="pcre2">(?i)cmd\.EXE</field>
  <field name="win.eventdata.parentCommandLine" type="pcre2">(?i)\s\/C\s</field>
  <options>no_full_log</options>
  <description>Suspicious Windows cmd shell execution</description>
  <mitre>
    <id>T1087</id>
    <id>T1059.003</id>
  </mitre>
  <group>sysmon,sysmon_eid1_detections,windows,</group>
</rule>
```

### After (`local_rules.xml`, this project)

```xml
<group name="ruleset_corrections,">

  <rule id="92032" level="3" overwrite="yes">
    <if_sid>92031, 61603</if_sid>
    <field name="win.eventdata.parentImage" type="pcre2">(?i)cmd\.EXE</field>
    <field name="win.eventdata.parentCommandLine" type="pcre2">(?i)\s\/C\s</field>
    <options>no_full_log</options>
    <description>Suspicious Windows cmd shell execution (generic parent/child pattern only, no command-content inspection — MITRE tags intentionally omitted per CISA/MITRE ATT&CK mapping guidance: insufficient evidence for T1087/T1059.003)</description>
    <group>ruleset_corrections,sysmon,sysmon_eid1_detections,windows,</group>
  </rule>

</group>
```

CISA/MITRE's own guidance frames the fallback as *"analysts will be limited to mapping to the tactic level"* when technique-level evidence is insufficient — not "map to nothing." Wazuh's `<mitre>` schema, however, only accepts technique/sub-technique IDs in its `<id>` field; the `tactic` value shown in an alert (e.g. `"tactic":["Discovery"]`) is derived automatically from whichever technique ID is present, not something a rule can set independently. There is no schema-native way to express "Discovery tactic, no specific technique" in a Wazuh rule. Given that constraint, removing the `<mitre>` block entirely is the closest available equivalent to CISA's "map to tactic level, not lower" guidance — it is a translation forced by the tooling, not a deviation from the guidance's intent.

### Verification — before/after, not assumed

The identical Atomic test was re-run after the `wazuh-manager` restart:

| | Before fix | After fix |
|---|---|---|
| Rule 92057 (T1059.001) | Fires, level 12, `mitre: T1059.001` | **Unchanged** — fires, level 12, `mitre: T1059.001` |
| Rule 92032 | Fires, level 3, `mitre: [T1087, T1059.003]` | Fires, level 3, **`mitre` field absent**, corrected description present |

Confirmed via direct alert-JSON comparison of the two runs, not inferred from the rule file alone.

## Why this matters

A single Atomic test surfaced two independent things worth knowing: (1) the technique itself is genuinely caught, correctly and at appropriate severity; (2) a bundled, out-of-the-box Wazuh rule was silently over-claiming ATT&CK coverage it hadn't earned — the kind of defect that only surfaces by reading a ruleset's actual field logic, not by trusting its label. Fixing it cost zero real detection coverage (three other, evidence-based `net.exe` rules already cover the legitimate T1087 case) and brought this specific rule in line with CISA and MITRE's own published mapping-quality standard.
