# T1055 — Process Injection

**Tactic:** Defense Evasion / Privilege Escalation (TA0005 / TA0004)
**Result:** ⚠️ **GAP FOUND AND CLOSED** — a genuine rule-coverage gap, later fixed and verified, plus one independently-discovered ruleset mistagging defect found and fixed along the way
**Test used:** [Atomic Red Team T1055, Test #3 — "Section View Injection"](https://github.com/redcanaryco/atomic-red-team/blob/master/atomics/T1055/T1055.md)

---

## Why this test

T1055's test list runs heavy — most candidates require either a Mimikatz-style download or a compiled external binary. Test #3 (`InjectView.exe`, shipped inside the atomics repo itself, no external download) was selected on the same dependency-light, single-technique criteria used throughout this capstone.

The dependency-light choice here reflects Atomic Red Team's own stated design goal, not an arbitrary preference of this project: Red Canary describes its tests as deliberately *"simple to understand, easy to execute, and repeatable... with minimal dependencies."* A purple-team methodology guide draws the boundary explicitly: Atomic Red Team is for validating detection coverage through a lightweight execute→check→tune→retest loop, and is not intended for advanced adversary emulation requiring custom implants — that belongs to a later Caldera phase in this project's own two-phase roadmap. A more APT-authentic injection technique is more appropriately deferred to that later phase than forced into this one for the sake of realism.

## Execution and result

```
Invoke-AtomicTest T1055 -TestNumbers 3
```

The technique (`InjectView.exe` → `notepad.exe` via `CreateRemoteThread`) genuinely executed — confirmed by a MessageBox popup and by Sysmon Event ID 8 (`SourceImage: InjectView.exe`, `TargetImage: ...Notepad.exe`).

Wazuh's `alerts.json` was searched exhaustively (by "InjectView", "T1055", and "notepad" keywords) — zero alerts correspond to the actual `CreateRemoteThread` event.

## Root cause: a rule-coverage gap, not a telemetry gap

Unlike the T1218 finding, this is not a data-collection problem. Sysmon's `CreateRemoteThread` include rule is broad and unconditional, so the event data reached Sysmon without difficulty. The gap is downstream, in Wazuh's ruleset — see the "Update" section below for the precise shape of that gap, refined in a later remediation pass.

## A second, independent finding surfaced while searching: rule 61618 mistagging

Searching Wazuh alerts for any sign of the injection also surfaced repeated firings of a completely unrelated default rule — **61618** ("Sysmon - Suspicious Process - svchost.exe", `level: 12`, `mail: true`, tagged `T1055` / Defense Evasion+Privilege Escalation) — for entirely routine Windows service startups (`svchost.exe -k LocalServiceRedirectionGuard -s EventSystem`, etc.), with no injection behavior involved at all.

Reading its actual XML:

```
<if_group>sysmon_event1</if_group>
<field name="win.eventdata.image">svchost.exe</field>
```

The only condition is: image name equals `svchost.exe`. That's it — no inspection of access rights, parent legitimacy, or path. Any process creation event named `svchost.exe` fires this rule at high severity with an email notification.

An exception rule exists (**61619**, `if_sid=61618`, suppresses to level 0 when `ParentImage` matches `\services.exe`) — but the observed events had `ParentImage: "-"` (Sysmon could not back-resolve the parent, a common boot-time condition), so the intended suppression never engaged, and the false alarm went through in full.

### Sourcing — a known, historically-documented false-positive generator

A Wazuh/OSSEC public mailing list post (groups.google.com/g/wazuh, May 2016) reports this exact rule description string producing *"one to two thousand"* false positives per hour from ordinary Windows activity — the example given at the time was NTP time sync. This is a first-party historical community record, not inference; the rule has carried this defect since at least 2016.

A more recent thread on the same mailing list (May 2023) shows **Wazuh's own support engineer** confirming the same rule family (61618/61638, covering `svchost.exe`, `dllhost.exe`, and other core Windows processes) still produces false positives, and directly recommending: *"I would recommend overwriting the rule with level 0, so you won't receive noisy alerts anymore."* This is a first-party, current, official-channel endorsement of exactly the override approach applied here — the only difference being that this fix keeps `level`/`mail` at their original values (12/true) rather than silencing to 0, since the goal was removing an unearned tag while preserving alert visibility, not suppressing the alert entirely.

### Correct T1055 detection — institutional sourcing

MITRE ATT&CK's own official Detection Strategies page, **DET0508** ("Behavioral Detection of Process Injection Across Platforms," created Oct 2025 / last modified May 2026 — current), specifies the correct data sources as Process Access (Sysmon EventCode=10), Process Creation (EventCode=1), and Module Load (EventCode=7), with `AccessMask` (e.g. `PROCESS_VM_WRITE`) as the key field distinguishing real injection from benign access. This directly matches:

- **Elastic's own official svchost-masquerade detection guidance** — checks process path under `System32`/`SysWOW64`, the `-k <service group>` command-line format, and the Microsoft code signature.
- **Splunk's official Enterprise Security detection content** for T1055, which also correlates access-mask/process-relationship data rather than name-matching.
- **Active Countermeasures** (a recognized threat-hunting research firm), which independently corroborates the same Event 8+10 + AccessMask correlation approach against a real Metasploit/Empire test case.

A bare `image: svchost.exe` match proves nothing about injection behavior — it fails the same evidentiary bar as the T1059.001/92032 finding in this series.

## Fix applied to 61618 — same standard, different target

Per the CISA/MITRE ATT&CK mapping guidance already applied to rule 92032 (see [T1059.001 finding](https://github.com/k0zzi/soc-lab-portfolio/blob/main/tools/red-team/findings/T1059.001.md)): remove the unearned tag rather than try to patch the broken suppression logic. The 61619 parent-based exception was deliberately **not** repaired as part of this fix — a `"-"`/unresolved parent is not a safe legitimacy signal to build an exception around, since it could itself be spoofed by a real attacker. `level`/`mail` (12/true) were left unchanged; only the unearned `T1055` tag was removed.

```
<rule id="61618" level="12" overwrite="yes">
  <if_group>sysmon_event1</if_group>
  <field name="win.eventdata.image">svchost.exe</field>
  <description>Sysmon - Suspicious Process - svchost.exe (generic image-name match only, no access-rights or process-relationship inspection — MITRE tag intentionally omitted per CISA/MITRE ATT&CK mapping guidance: insufficient evidence for T1055)</description>
  <group>ruleset_corrections,windows,sysmon,sysmon_process-anomalies,</group>
</rule>
```

### Verification — a genuine before/after, including a diagnostic detour worth documenting

The first re-test attempt (a non-boot-time `svchost.exe` restart) appeared to show "no change" — this turned out to be because rule 61619's suppression legitimately fired and silenced the alert under that condition (correct behavior, not a fix failure). To reproduce the actual target scenario — a boot-time `svchost.exe` with an unresolved `ParentImage: "-"`, where 61619 does *not* engage — CLT601 was rebooted.

|                  | Before fix (09:21:33, boot-time, `ParentImage: "-"`) | After fix (10:15:24, same condition, 7 separate firings) |
| ---------------- | ---------------------------------------------------- | -------------------------------------------------------- |
| `mitre` block    | `{"id":["T1055"], ...}` present                      | Absent entirely                                          |
| `level` / `mail` | 12 / true                                            | Unchanged — 12 / true                                    |
| Description      | Original                                             | Corrected text present                                   |

Confirmed via direct alert-JSON comparison at the actual reproduced boot-time condition, not a surface-level re-test.

## Update — root cause refined, gap closed (later remediation session)

Two corrections to the original finding above, discovered while building the fix:

1. **"No rule at all inspects Event 8/10" was imprecise.** Wazuh's default ruleset does carry Event 8 rules (92400–92403) and an Event 10 rule (92900) — but 92400/92401/92403 are narrowly scoped to `explorer.exe`, `mstsc.exe`, and `lsass.exe` as *targets*, and none of the four inspects `StartModule`/`StartFunction`. `notepad.exe` (this test's actual target) was never in scope for any of them. The gap is real, just narrower than originally stated: a target-list gap plus a missing-signal gap, not a total absence of coverage.

2. **`archives.json` is now populated** in this deployment (`logall_json` was enabled during a later remediation pass) — the original evidentiary caveat about transport-vs-matching ambiguity no longer applies. Re-running this exact test with archiving on confirmed Event 8 reaches Wazuh: `SourceImage: InjectView.exe`, `TargetImage: ...Notepad.exe`, `StartModule: -`, `StartFunction: -`.

### Fix: rule 100230 (Event 8, target-agnostic)

`StartModule`/`StartFunction` showing `-` (unresolved) is documented by TrustedSec's SysmonCommunityGuide as the strongest signal available on Event 8: injected code runs from memory, not a loaded DLL, so Sysmon cannot resolve a source module for the new thread. Microsoft's own Sysmon documentation confirms the field is inference-based and legitimately empty when the start address falls outside all loaded modules. MITRE's DET0295 (T1055.003, Oct 2025) names Event 8 alongside Event 10 as a correct data source for this technique family.

Wazuh's `windows_eventchannel` decoder does not parse `StartModule`/`StartFunction` into `win.eventdata.*` — confirmed by inspecting a live Event 8 record's decoded field list. The rule instead matches `StartModule: -` directly against `full_log` via Wazuh's `<match>` directive, which operates on the raw message text independent of decoder field extraction.

```
<rule id="100230" level="14">
  <if_group>sysmon_event8</if_group>
  <match>StartModule: -</match>
  <field name="win.eventdata.sourceImage" type="pcre2" negate="yes">(?i)(MsMpEng\.exe|WmiPrvSE\.exe|csrss\.exe|wininit\.exe)</field>
  <options>no_full_log</options>
  <description>CreateRemoteThread from $(win.eventdata.sourceImage) into $(win.eventdata.targetImage) with unresolved StartModule/StartFunction — strong indicator of shellcode/memory-backed injection (T1055)</description>
  <mitre><id>T1055</id></mitre>
  <group>atomic_red_team_detections,</group>
</rule>
```

Before deployment, every historical Event 8 record in this environment was queried for `StartModule=-`: only the known-malicious test tool (`InjectView.exe`) produced it — zero legitimate processes in this deployment's history share the signal. Deployed and re-tested against the exact same Atomic Red Team command as the original finding:

```
Invoke-AtomicTest T1055 -TestNumbers 3
```

Fired immediately, `level: 14`, `mail: true`, `firedtimes: 1` — the exact injection this finding originally reported as undetected.

### Fix: rules 92910/92920 (Event 10, target-scoped)

The existing Event 10 rules for `explorer.exe` (92910) and `mstsc.exe` (92920) had the same defect as 61618: a bare target-image match with no access-rights inspection at all. Both were corrected with a `GrantedAccess` allowlist sourced from TrustedSec's SysmonCommunityGuide and Splunk Enterprise Security's "Windows Process Injection" analytics (`0x40`, `0x1fffff`, `0x1010`, `0x1438`, `0x143a`, `0x1f0fff`, `0x147a`, `0x0820`).

### New rule: 100220 (Event 10, target-agnostic) — known limitation

A parallel target-agnostic Event 10 rule (100220) was added using the same mask list, per MITRE DET0508. Live testing surfaced a real false positive: `powershell.exe` accessing small utility processes (`HOSTNAME.EXE`, `whoami.exe`, itself) under .NET's JIT-compiled execution model also produces `GrantedAccess: 0x1fffff` and an `UNKNOWN`-containing `CallTrace` — ruling out `CallTrace` content as a usable discriminator in this environment. This rule remains deployed (it covers Event 10-based injection variants that do call `OpenProcess`, which this specific test does not) but is documented here as needing further tuning before it can be considered production-reliable.

## Result summary (updated)

Three findings from a single Atomic test, spanning two remediation sessions: (1) a rule-coverage gap — the default ruleset's Event 8/10 rules existed but were too narrowly targeted and ignored the strongest available injection signal — now closed via rule 100230, verified live against the original reproduction steps; (2) an unrelated, independently-discovered mistagging defect in rule 61618, fixed and verified with a real before/after comparison; (3) the related Event 10 rules (92910/92920) brought up to the same evidentiary standard, plus a new target-agnostic Event 10 detection (100220) with a documented, unresolved false-positive limitation.
