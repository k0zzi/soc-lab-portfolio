# T1218 — System Binary Proxy Execution (LOLBAS)

**Tactic:** Defense Evasion (TA0005)
**Result:** ❌ **MISSED** — a telemetry-layer gap, not a SIEM rule gap
**Test used:** [Atomic Red Team T1218, Test #15 — "LOLBAS Msedge to Spawn Process"](https://github.com/redcanaryco/atomic-red-team/blob/master/atomics/T1218/T1218.md)

---

## Why T1218 and T1055 are tracked as two separate techniques, not one "LOLBin" slot

Both live under a single conceptual "LOLBin" category in this capstone's kill-chain plan, but each gets its own isolated run, its own log verification, and its own write-up — following Redfox Cybersecurity's purple-team guidance that *"each atomic maps to a single technique and is easy to stop, revert, and discuss."* T1218 and T1055 are distinct MITRE technique IDs with distinct root causes; collapsing them into one finding would have hidden that.

## Why this test

T1218 has 16 predefined Atomic tests, ranging from DLL-injection/registry-abuse tools to single-line LOLBAS invocations. Test #15 was selected on the same criteria used throughout this capstone:

- **Zero dependencies** — no external file download (unlike #12, which pulls an `.inf` file from GitHub).
- **A "pure" T1218 test** — no bleed into a second technique (unlike #13, which also renames `calc.exe` to `explorer.exe`, bleeding into T1036 Masquerading).
- **Authoritative sourcing** — the [LOLBAS project](https://lolbas-project.github.io/lolbas/Binaries/Msedge/) (the industry-standard living-off-the-land binaries database), not a practitioner blog.
- **Full self-cleanup** via `taskkill` on both `msedge.exe` and `calc.exe`.

The technique abuses Microsoft Edge's legitimate `--gpu-launcher` flag — meant to launch Edge's own GPU helper process — to instead launch an arbitrary binary (`calc.exe` as the safe stand-in) as a child of the trusted, Microsoft-signed `msedge.exe`. It tests whether the ruleset flags an unusual parent/child pairing like this, or trusts it by virtue of the signed parent.

```
msedge.exe --disable-gpu-sandbox --gpu-launcher="calc.exe"
```

## Execution

```powershell
Invoke-AtomicTest T1218 -TestNumbers 15
```

The technique genuinely executed — Calculator visibly opened on CLT601's screen, confirming this was a real, functioning technique run, not a scripting error.

## Result: zero telemetry, not a missed alert

An exhaustive Sysmon query (`Get-WinEvent -FilterHashtable` with an explicit start/end time window, server-side filtered — no client-side truncation that could hide results) found **zero Calculator/UWP process-creation events of any kind** in the Sysmon log for that window. Only `msedge.exe` and the cleanup `taskkill.exe` events appeared. This is not "an event existed and no rule matched it" — it is "no event was ever generated." No Wazuh rule, however well written, could have caught this technique, because the underlying data point never existed.

## Root cause — Sysmon's ProcessCreate allowlist doesn't cover UWP/AppX activation

Direct inspection of the live `sysmon64.exe -c` rule dump on CLT601 confirmed the deployed config's ProcessCreate section is:

```
onmatch: include, combine using Or
```

— a strict **allowlist** of roughly 150 specific, technique-tagged binaries and command-line patterns (`net.exe`, `whoami.exe`, `powershell.exe`, `rundll32.exe`, etc.). Anything not on that list produces no Sysmon Event 1 at all.

Modern Windows Calculator is not a conventional `.exe` launched by path — it runs as a packaged **UWP/MSIX app**, invoked via **DCOM/AppX server activation**, with a command line that looks like:

```
...\Calculator.exe -ServerName:App.AppX<hash>.mca
```

(Pattern confirmed against a real, published Sysmon Event 1 example from Roberto Rodriguez / Cyb3rWard0g — HELK/OTRF founder and a recognized threat-hunting researcher, also the author of the SigmaHQ `comsvcs.dll` LSASS-dump detection rule referenced in the T1003.001 finding.) This activation pattern matches none of the roughly 150 allowlist entries, so Sysmon never generates a process-creation event for it — regardless of what the parent process was, or how the child was launched.

## This is a documented, author-acknowledged trade-off — not a misconfiguration

The lab runs Olaf Hartong's [sysmon-modular](https://github.com/olafhartong/sysmon-modular) config, fetched and inspected directly from the live repository. Its generated `sysmonconfig.xml` carries this exact embedded comment:

> *"NOTICE: This is a balanced generated output of Sysmon-modular with medium verbosity — due to the balanced nature of this configuration there will be potential blind spots."*

The same repository documents four tiers:

| Tier | Coverage model | This lab |
|---|---|---|
| Default / "balanced" | Allowlist (`onmatch: include`) | ✅ Deployed |
| Verbose (`sysmonconfig-excludes-only.xml`) | *"All events are included, only the exclusion modules are applied"* — would have caught this event | Not deployed |
| Super-verbose / research | Maximum detail, not intended for production | Not deployed |
| MDE-augmentation | Sysmon + Microsoft Defender for Endpoint telemetry combined | Not deployed |

The author's own documented remedy for exactly this class of blind spot is moving to the excludes-only tier — at the explicitly acknowledged cost of significantly higher log volume and performance impact. That trade-off is a deliberate, sourced engineering decision, not something to silently work around mid-assessment (see "Why this isn't fixed here" below).

## Why this finding is more severe than the T1059.001/92032 mistagging finding

The [T1059.001 finding](./T1059.001.md) in this same series documented a **SIEM-layer defect**: data reached Wazuh, but a rule statically applied ATT&CK tags it hadn't earned. This finding is a **telemetry-layer defect**: no data reached Wazuh at all, because Sysmon itself never generated the underlying event. The two categories require entirely different fixes — a rule edit versus a data-source configuration change — and the telemetry-layer category is the more serious of the two, because no amount of downstream rule sophistication can compensate for it.

## Why this isn't fixed here

Changing the Sysmon config tier is a data-source-level change, not an isolated rule edit — unlike the 92032 override, it would affect every subsequent technique's baseline. Per [NIST SP 800-115](https://www.nist.gov/) (Technical Guide to Information Security Testing and Assessment), a structured security assessment separates the testing phase from the remediation phase specifically to preserve *"a standardized process [that] allows you to compare results across assessments."* Changing the underlying telemetry source mid-run would make the remaining techniques' results incomparable to this one and to each other. The config-tier change is documented here as a sourced, ready-to-implement fix, and queued into a single remediation pass applied only after all six techniques in this series are complete.
