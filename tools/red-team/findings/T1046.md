# T1046 — Network Service Discovery

**Tactic:** Discovery (TA0007)
**Result:** ❌ **MISSED at the endpoint layer** — but ✅ **genuinely caught and auto-contained at the network perimeter**, invisibly to the SIEM
**Test used:** [Atomic Red Team T1046, Test #10 — "Port-Scanning /24 Subnet with PowerShell"](https://github.com/redcanaryco/atomic-red-team/blob/master/atomics/T1046/T1046.md)

This is the last technique in this series and the most layered finding: two independent defensive systems reacted to the same activity in completely different ways, and neither was aware of the other's result.

---

## Why this test

T1046 offers 13 predefined tests. Eliminated: #1/#2/#12 (Linux/macOS only), #3 (nmap installer download), #4 (Python installer download), #5–8 (the WinPwn framework — an external, hacktool-classed download; #7 alone runs ~600 seconds), #9 (requires Docker, not present), #13 (RustScan plus a Visual C++ Redistributable download). That left two zero-dependency, native-PowerShell candidates: Test #10 and Test #11.

**Test #10** ("Port-Scanning /24 Subnet with PowerShell") was chosen over **Test #11** ("Remote Desktop Services Discovery," a single local `Get-Service` call with no network connection at all — a weak fit for "network *service discovery*"). Test #10's default ports (445, 3389) are directly confirmed by MITRE ATT&CK's own official T1046 procedure-example table: **InvisiMole** *"can scan the network for open ports and vulnerable instances of RDP and SMB protocols"* and **Magic Hound** *"used KPortScan 3.0 to perform SMB, RDP, and LDAP scanning"* — the exact same port pair, named in MITRE's own database, not an arbitrary default.

## Execution and endpoint-layer result

```
Invoke-AtomicTest T1046 -TestNumbers 10 -InputArgs @{ip_address="10.1.20.10"}
```

(Target selection reasoning — SRV201 directly, not a blind subnet sweep — is covered in the [T1018/T1087.002 finding](https://github.com/k0zzi/soc-lab-portfolio/blob/main/tools/red-team/findings/T1018-T1087.002.md); the same AD-recon chain logic applies here, and this test ran immediately after AdFind had already revealed SRV201 as the DC.)

The scan genuinely executed: 254 hosts × 2 ports (508 connection attempts), finding port 445 open on both SRV201 (10.1.20.10) and SRV202 (10.1.20.11).

A Wazuh alert search scoped correctly to **CLT601's own agent ID** (network-connection telemetry is generated by the connection-initiating host, not the target — an earlier search mistakenly checked SRV201's agent records and returned unrelated FIM noise) found **zero Sysmon Event 3 (NetworkConnect) records** for this activity. The only Event 3 records present in the surrounding window were unrelated Windows Defender outbound HTTPS connections. The only trace of the technique at all was indirect: rule 92027 (T1059.001, PowerShell-spawns-PowerShell) captured the wrapper process's full command line — confirming the correct target and ports were used — but this is process-creation telemetry, not network-connection telemetry.

### Root cause — same mechanism as the T1218 finding

Olaf Hartong's sysmon-modular NetworkConnect (Event 3) section uses an `onmatch:include` allowlist that only logs MITRE-technique-tagged connection patterns. This is the identical root cause documented in the [T1218 finding](https://github.com/k0zzi/soc-lab-portfolio/blob/main/tools/red-team/findings/T1218.md), not a coincidence: both techniques used a native OS mechanism (UWP activation; raw TCP sockets) that Sysmon's allowlist model was never built to recognize by default. (This claim is refined below, in the Update section, once a later retest surfaced a more complete picture of what the allowlist does and doesn't cover.)

### Why this is a compounded, two-layer gap — even with telemetry, current rules would still miss it

Three independent, current institutional/vendor sources confirm this technique class genuinely requires more than a single static rule:

1. **MITRE ATT&CK's own Detection Strategies object DET0376** ("Behavioral Detection Strategy for Network Service Discovery Across Platforms," created Oct 2025), analytic AN1057: requires correlating Sysmon EventCode=1 (process creation) **and** EventCode=3 (network connection) within a time window against a configurable `ScanRateThreshold`/`TimeWindow`.
2. **Elastic's official production rule "Potential Network Scan Detected"** is explicitly threshold-based — connection attempts from a single source to a wide range of destination ports within a window — not single-event.
3. **Splunk's official "Advanced IP or Port Scanner Execution" analytic** instead keys on known-tool process-creation signatures (tool name, CLI flags like `/portable`) — which also would not catch a native `.NET TcpClient` call carrying no distinguishing tool signature.

So even if Event 3 telemetry existed, neither this project's newly-deployed rules (100190/100200, both single-condition field matches) nor a name-based signature approach would catch this specific technique variant — a real fix requires a new class of Wazuh rule (frequency/timeframe composite) not yet built anywhere in this project.

## The network perimeter DID react — a pre-existing, previously-built automation

Shortly after the scan, CLT601 lost all outbound connectivity. The cause, recovered from an earlier project session's automation work: **Suricata's built-in ET SCAN ruleset** detected the 508-connection scan pattern and fired **Suricata rule 86601**, which reaches Wazuh via the OPNsense agent and triggers an existing custom rule (**100100**) that filters for ET SCAN alerts. That rule feeds a pre-built Shuffle workflow (`port-scan-auto-block`), which calls the OPNsense API to add the source IP to a `shuffle_blocked_IPs` alias, enforced by a floating firewall rule across all interfaces.

A live capture from OPNsense's own "Firewall: Log Files: Live View" confirmed the exact, correctly-targeted block:

```
VLAN60  In  block  10.1.60.10 → 10.1.20.19:3389   Shuffle SOAR Auto-Block Alias Floating Rule
VLAN60  In  block  10.1.60.10 → 10.1.20.24:445    Shuffle SOAR Auto-Block Alias Floating Rule
```

(timestamps matching the scan window exactly)

This means the Suricata alert **does** reach Wazuh and **does** trigger an existing custom rule — this is not the same telemetry gap as the Sysmon Event 3 issue. Network-layer defense-in-depth genuinely worked here, automatically, without any manual intervention.

## But the SIEM has no record that containment actually happened

Two separate, confirmed gaps keep this success invisible to anyone looking only at Wazuh:

**Gap 1 — the SOAR's own action is never logged back to Wazuh specifically, though a record exists elsewhere.** Checked directly, not assumed: the `port-scan-auto-block` workflow's TheHive step did fire correctly — case **#1024, "Port Scan Detected - 10.1.60.10"**, created at 11:02 on the exact date and window of this test, correctly attributing CLT601 as the source. So a human-visible record of the containment action does exist. The gap is narrower and more specific than "no record anywhere": the Suricata alert reaching Wazuh (rule 100100) is one event, tracked in the SIEM; the fact that Shuffle *actually blocked the IP* is a separate outcome recorded only in TheHive, a different platform, with no link back to the originating Wazuh alert or rule ID. Direct inspection of the OPNsense Wazuh agent's `ossec.conf` confirms only three `<localfile>` sources are defined (Suricata `eve.json`, `active-responses.log`, `opnsense_syslog.log`) — none capture the SOAR's remediation outcome, so Wazuh itself has no way to show "alert X resulted in containment action Y" as a single correlated record, even though each half is independently visible in its own tool.

**Gap 2 — OPNsense's own firewall log never reaches Wazuh at all.** The floating rule's actual pass/block decisions live in `filterlog` (`/var/log/filter/latest.log`, RFC5424 syslog format, root-only permissions) — a completely separate data source from the Suricata IDS alert stream. Direct inspection confirmed `opnsense_syslog.log` (the file Wazuh's agent does watch) contains exclusively `suricata[pid]:` log lines; the block decision itself, visible only in OPNsense's own web UI or in `/var/log/filter/`, has no forwarding path to Wazuh.

### Sourcing for why both of these matter

**NIST SP 800-61** (Computer Security Incident Handling Guide) names firewall/network-device logs as a standard incident-detection data source, and calls for recording actions taken as part of incident documentation — supporting that a SOAR's own containment actions should be logged back to the SIEM, not just the alert that triggered them. This is the general industry concept of **closed-loop SOAR-SIEM integration**: containment actions generate their own audit trail, feeding back into the same platform that raised the alert.

## Why these two gaps aren't fixed here

Both are documented as sourced, ready-to-implement fixes, deliberately deferred to the same batched remediation pass referenced throughout this series. Per **NIST SP 800-115**'s five-phase structure (Planning → Discovery → Attack/Exploitation → Post-Testing/Reporting), remediation belongs strictly after the testing phase, specifically to preserve *"a standardized process [that] allows you to compare results across assessments."* Gap 1 (filterlog forwarding) was closed in a later remediation session — see the Update section below. Gap 2 (closed-loop SOAR-action correlation) remains open.

## Update — endpoint retest, and a correction to the original root-cause claim

A later remediation session re-ran this test with explicit targets instead of a full subnet sweep, to isolate the mechanism precisely:

```
Invoke-AtomicTest T1046 -TestNumbers 10 -InputArgs @{ "ip_address" = "10.1.20.10,10.1.20.11" }
```

This produced **two** Sysmon Event 3 records — the two genuinely successful port 445 connections (SRV201, SRV202). The port 3389 attempts against both targets produced zero telemetry.

This refines, and partly corrects, the root-cause claim above. The original explanation — that Sysmon's NetworkConnect allowlist excludes a generic `TcpClient` call from `powershell.exe` entirely — was incomplete: the Balanced config does carry an include rule tagging PowerShell's outbound connections generically (`technique_id=T1059.001`), which is exactly what produced these two records. The real reason the original 254-host sweep showed zero events is simpler and better-documented: Microsoft's own Sysmon guidance (a Microsoft Learn thread, accepted community answer) confirms Event 3 **only fires for established connections** — *"network connection block or reset logging is not currently available through Sysmon."* Across 508 connection attempts against mostly non-existent or closed targets, only genuinely successful connections could ever produce an event; nearly all of them timed out or were refused, which is why the original test appeared to generate zero telemetry.

Even where telemetry now exists, it does not help: the tag on these two records (`T1059.001`, "PowerShell") reflects "PowerShell made a network connection," not "a scan occurred" — a Wazuh alert search scoped to both the target IPs and the agent+timestamp window found zero alerts. This confirms the finding as originally scored rather than reversing it: telemetry is asymmetric (only successful connections are visible, and the volume that matters for scan detection — the failures — is invisible by design) and semantically wrong for this use case even when present. The institutional case for why a frequency/timeframe composite rule (not a single-event rule) is required — MITRE DET0376, Elastic, Splunk — stands unchanged.

Also updated since the original finding: **Gap 1 above (OPNsense filterlog never reaching Wazuh) is now closed** — filterlog forwarding was implemented and verified in a later remediation session (working threshold detection, rules 87701→87702). Gap 2 (linking a Wazuh alert to its own downstream SOAR containment outcome as one correlated record) remains open.

## Result summary

T1046 is the most nuanced finding in this capstone: **missed** at the endpoint/Sysmon/Wazuh-rule layer (a compounded telemetry-plus-detection-architecture gap, institutionally sourced via MITRE DET0376, Elastic, and Splunk, and further clarified on retest), but genuinely **caught and auto-contained** at the network perimeter through a pre-existing Suricata/Wazuh/Shuffle/OPNsense automation chain, which correctly produced a human-visible record (TheHive case #1024) — confirmed live, not assumed. The precise gap is narrower than "invisible everywhere": Wazuh itself cannot yet show an alert and its own automated containment outcome as one correlated record, but the containment action is not undocumented — it simply lives in a different tool than the one that raised the alert, and the underlying firewall-log visibility gap has since been closed. This closes all six techniques in this test series.
