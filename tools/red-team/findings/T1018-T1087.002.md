# T1018 & T1087.002 — Remote System Discovery & Domain Account Discovery

**Tactic:** Discovery (TA0007)
**Result:** ✅ **CAUGHT** — both techniques, both by newly-deployed custom rules ported from SigmaHQ
**Tests used:** [Atomic Red Team T1018, Test #1 — "Remote System Discovery - net"](https://github.com/redcanaryco/atomic-red-team/blob/master/atomics/T1018/T1018.md) and [T1087.002, Test #7 — "Adfind - Enumerate Active Directory User Objects"](https://github.com/redcanaryco/atomic-red-team/blob/master/atomics/T1087.002/T1087.002.md)

These two techniques are documented together, not split into separate files: they were run as a single operational step in this capstone's kill-chain plan (an "AD recon" stage), against the same target, using the same threat-actor sourcing, with AdFind's own execution determining the follow-on target for `net view`. Splitting them would obscure that operational link. This grouping choice follows CISA and MITRE ATT&CK's own report-structuring guidance ("Best Practices for MITRE ATT&CK Mapping," Table 4): group by operational stage, but keep each technique's own ID and evidence clearly separate within that stage — which is exactly the structure used below.

---

## Why these two techniques and tests — cross-validated across four independent source categories

1. **MITRE ATT&CK's own S0552 (AdFind) software page** (last modified 25 Sept 2024) lists 11 named threat groups using this tool, spanning both defunct (Trickbot, Ryuk, Maze) and currently active (Akira, Play, BlackByte, INC Ransom, APT29) actors — and tags AdFind to both T1018 and T1087.002.
2. **CISA's official joint #StopRansomware advisory AA24-109A** — co-authored with the FBI, the Netherlands' NCSC-NL, and the **US Department of Defense Cyber Crime Center** as a listed agency, most recently updated 13 November 2025 — names AdFind by name in its official "Tools Leveraged by Akira Ransomware Actors" table.
3. **AttackIQ**, a defense-industry adversary-emulation vendor, published an updated attack-graph response to AA24-109A in November 2025 operationalizing this exact data into scenarios explicitly named *"Enumerate Domain Controllers using Nltest (T1018)"* and *"Active Directory Discovery using AdFind (T1018)"* — arriving independently at the same T1018+AdFind pairing selected here.
4. **ransomware.live** (a live ransomware-tracking threat-intel aggregator), dated 2026-07-23, documents INC Ransom (an active group) currently using AdFind alongside Advanced IP Scanner and SoftPerfect NetScan for AD/network discovery ahead of exfiltration, with a ready detection query.

No other technique pair in this capstone has this breadth of independent, current sourcing — spanning a MITRE software page, a joint government/DoD advisory, a commercial adversary-emulation vendor, and live threat-intelligence tracking.

## Test content — verified against the local install, not just GitHub

Before running either test, the local `.md`/`.yaml` copies on CLT601 were checked against the initially-referenced GitHub content (a Gate 1 practice re-applied after a lapse earlier in this same series, where GitHub content was used without the live-system check). T1018 Test #1 matched exactly (GUID `85321a9c-897f-4a60-9f20-29788e50bccd`). T1087.002 Test #7's local copy carried one addition not present in the initially-fetched GitHub commit — an `optional_args` input parameter, default empty, no behavioral change — confirming the local install was slightly newer; the local version was treated as authoritative.

## Target selection for T1018 — why targeting the DC directly is the realistic choice, not a shortcut

CLT601 (10.1.60.10) has no *a priori* knowledge of SRV201's IP (10.1.20.10) as a human operator would understand "knowledge" — but Microsoft's own official **Domain Controller Locator** documentation describes how any domain-joined computer's Netlogon service automatically resolves its DC via DNS SRV records (`_ldap._tcp.dc._msdcs.<domain>`) as a normal part of AD membership, with no adversary action required. This was independently confirmed in-session: when T1087.002's AdFind test ran, it printed `Using server: SRV201.soc.dev:389` without being told which server to use — it located the DC through this exact mechanism. Targeting SRV201 directly for the T1018 scan is therefore not a shortcut around realism; it reflects genuine attacker behavior in an AD environment, and matches the documented AA24-109A sequence (AD-discovery tool first, then targeted scanning of what it revealed).

## Execution and results

**T1018 Test #1:**
```powershell
Invoke-AtomicTest T1018 -TestNumbers 1
```
`net view /domain` + `net view` executed. Caught by Wazuh's **default** ruleset even before any custom rule was deployed: rules **92034** and **92035**, both correctly tagged `T1018`.

**T1087.002 Test #7:**
```powershell
Invoke-AtomicTest T1087.002 -TestNumbers 7 -GetPrereqs
Invoke-AtomicTest T1087.002 -TestNumbers 7
```
AdFind (`-f (objectcategory=person)`) ran successfully against SRV201, returning 5 real AD user objects (Administrator, Guest, krbtgt, and two named accounts). Before any custom rule was deployed, this was **only partially visible** in Wazuh's default ruleset — rule 92203 (T1105, Ingress Tool Transfer, for the file write) and rule 92052 (T1059.003, for the `cmd.exe` wrapper) fired, but nothing tagged the activity as `T1087.002` by name.

### A genuine Defender finding along the way

During `-GetPrereqs`, Windows Defender blocked the specific subprocess-spawn pattern Invoke-AtomicRedTeam uses to download AdFind.exe — confirmed via `Get-MpThreatDetection` (ThreatID 2147849223), with the command line and timestamp matching exactly. A manual `Invoke-WebRequest` of the identical URL in the current session succeeded without issue. This isolates the block to the encoded-child-process spawn *behavior* Invoke-AtomicRedTeam uses, not to AdFind.exe's hash, signature, or download URL — AdFind's own author (joeware.net) independently confirms that anti-malware products commonly flag AdFind as a LOLBIN/PUA due to its ransomware associations, which is consistent with this being a behavior-level block rather than a false positive on the tool itself.

## Deploying real detection rules — ported from SigmaHQ, not left as unwritten placeholders

This project's own `tools/blue-team/sigma/` folder — planned in the repo's structure documentation — had no actual `t1018-net-discovery.yml`/`t1087-adfind-execution.yml` files in it; these were named in earlier planning but never materialized as real files, committed or otherwise. Rather than write them now as untested, from-scratch rules, two currently-maintained SigmaHQ rules were ported directly into real Wazuh local rules — rules that happen to reference the exact same Atomic Red Team commits used for testing here:

- `proc_creation_win_net_view_share_and_sessions_enum.yml` (SigmaHQ id `62510e69`) → Wazuh rule **100190** (level 6, matches `net.exe`/`net1.exe` + `view` in commandline, excludes UNC-path commandlines)
- `proc_creation_win_pua_adfind_susp_usage.yml` (SigmaHQ id `9a132afa`) → Wazuh rule **100200** (level 12, `mail: true`, matches AdFind's known recon-flag list including `objectcategory=`)

```xml
<group name="atomic_red_team_detections,">

  <rule id="100190" level="6">
    <if_sid>61603</if_sid>
    <field name="win.eventdata.originalFileName" type="pcre2">^net\.exe$|^net1\.exe$</field>
    <field name="win.eventdata.commandLine" type="pcre2">view</field>
    <field name="win.eventdata.commandLine" negate="yes" type="pcre2">\\\\</field>
    <description>Share and session enumeration via net.exe/net1.exe "view" flag (T1018) — ported from SigmaHQ proc_creation_win_net_view_share_and_sessions_enum.yml (id 62510e69)</description>
    <mitre><id>T1018</id></mitre>
    <group>attack_discovery,sigma_ported,</group>
  </rule>

  <rule id="100200" level="12">
    <if_sid>61603</if_sid>
    <field name="win.eventdata.commandLine" type="pcre2">(?i)domainlist|trustdmp|dcmodes|adinfo|-sc dclist|computer_pwdnotreqd|objectcategory=|-subnets -f|name="Domain Admins"|-sc u:|domainncs|dompol| oudmp |subnetdmp|gpodmp|fspdmp|users_noexpire|computers_active|computers_pwdnotreqd</field>
    <description>AdFind (or renamed equivalent) execution with common AD-recon flags (T1087.002) — ported from SigmaHQ proc_creation_win_pua_adfind_susp_usage.yml (id 9a132afa)</description>
    <mitre><id>T1087.002</id></mitre>
    <group>attack_discovery,sigma_ported,</group>
  </rule>

</group>
```

Both placed in a new `atomic_red_team_detections` group — deliberately kept separate from `ruleset_corrections`, which is reserved for overwriting existing default-ruleset defects (see the T1059.001 and T1055 findings), not for net-new detections.

## Verification — clean before/after, since a default-rule baseline already existed

After a `wazuh-manager` restart, both tests were re-run:

- **100190** fired correctly on both `net view /domain` and `net view` (T1018, level 6).
- **100200** fired correctly on the AdFind commandline (T1087.002, level 12, `mail: true`) — the same commandline that, before deployment, had produced only the indirect/mistagged alerts described above. This is the cleanest before/after in this entire capstone: identical input, identical Wazuh manager, the only variable being the newly-added rule.

## Severity calibration — checked against major-vendor practice after deployment

Two official vendor sources were checked to confirm the level-12/`mail:true` choice for rule 100200 wasn't excessive:

- **Elastic's own official "AdFind Command Activity" rule** (broad, name-only match — not flag-specific like ours) runs at `Severity: low, Risk score: 21` and explicitly states: *"This rule has a high chance to produce false positives as it is a legitimate tool used by network administrators... consider adding exceptions — preferably with a combination of user and command line conditions."* It also advises: *"Malicious behavior with AdFind... doesn't happen in isolation, so reviewing previous logs/activity... can be very telling."*
- **Splunk's official "Detection: Windows AdFind Exe" analytic** (names Wizard Spider and FIN6) runs via Risk-Based Alerting by default — `Disabled: true`, contributing to a risk score rather than firing a standalone critical alert — and ships a customer-tunable, empty-by-default false-positive filter macro for exactly this purpose.

Neither vendor treats a bare "AdFind ran" event as critical-severity in isolation. The level-12 choice here is defensible on its own terms because the ported rule is *flag-specific* (requires known recon flags like `objectcategory=`), not name-only like Elastic's broad rule — but the mature refinement both vendors point to is a **user/commandline-scoped exception** for known legitimate admin usage, not a blanket severity reduction. This lab has no real, recurring legitimate-AdFind-usage account to scope such an exception around, so writing one now would itself be an unevidenced rule — the same anti-pattern the CISA/MITRE mapping-guidance fixes elsewhere in this series have been correcting. This is documented here as a sourced, ready-to-implement refinement for a real deployment, deliberately not applied in this lab.

## Result summary

Both techniques caught — T1018 by Wazuh's default ruleset alone, T1087.002 only after this project's own custom rule was deployed and verified with a clean before/after comparison. Along the way: a genuine Defender-behavior finding (subprocess-spawn pattern blocked, not the tool itself), and a sourced, deliberately-unapplied severity refinement recommendation matching Elastic and Splunk's own stated practice.
