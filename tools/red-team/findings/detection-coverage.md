# Detection Coverage Summary — Atomic Red Team Capstone

Six MITRE ATT&CK techniques (seven counting the two sub-techniques scored separately in the AD-recon step) were tested against this lab's live Wazuh/Sysmon/Suricata/Shuffle stack. Scores below use [DeTT&CT](https://github.com/rabobank-cdc/DeTTECT)'s own official detection scoring scale — DeTT&CT (Detect Tactics, Techniques & Combat Threats), developed and maintained by Rabobank's CDC team, is the industry-standard open-source framework for scoring and visualizing ATT&CK-based detection coverage, and is the tool this project has designated for pre/post capstone coverage comparison.

## Scoring scale used (verbatim from DeTT&CT's official wiki)

| Score | Name                | Description                                                                                                                                        |
| ----- | ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| -1    | None                | No detection.                                                                                                                                      |
| 0     | Forensics / context | No detection, but the technique is being logged for forensic purposes and can be used to provide context.                                          |
| 1     | Basic               | A basic signature detects a specific part of the technique's procedures. Minimal aspects covered; false negatives high.                            |
| 2     | Fair                | A (correlation) rule covers more aspects of the technique's procedures than a basic signature; false negatives lower but may still be significant. |
| 3     | Good                | Effective, real-time detection using more complex analytics; many known aspects covered.                                                           |
| 4     | Very good           | Very effective, real-time detection covering almost all known aspects; harder to bypass.                                                           |
| 5     | Excellent           | Same as "Very good" but all known aspects of the technique's procedures are covered.                                                               |

Scores here are assigned conservatively — none of this lab's rules involve genuine cross-event correlation or advanced analytics, so no technique is scored above "2 / Fair," even where a rule performs its narrow job well.

## Update — remediation pass changes reflected above

Four changes since the original coverage table, across two remediation sessions:

- **T1055 moved from 0/Forensics to 2/Fair.** The rule-coverage gap this finding originally reported is now closed. Rule 100230 (Sysmon Event 8, matching `StartModule: -` — sourced from TrustedSec's SysmonCommunityGuide and MITRE DET0295) was deployed and verified live against the exact original reproduction steps, firing correctly with zero false positives across this environment's full Event 8 history. The related Event 10 rules (92910, 92920) were also corrected to inspect `GrantedAccess`, closing the same evidentiary gap identified in the 61618 mistagging finding. A parallel, more general Event 10 rule (100220) was also added but carries a known, unresolved false-positive source (`.NET` JIT-compiled `CallTrace` entries) — documented in the T1055 finding rather than allowed to inflate this score.
- **T1046's endpoint score revised from -1/None to 0/Forensics/context.** A retest using explicit targets (rather than a full 254-host sweep) showed Sysmon Event 3 *does* fire for genuinely successful connections under the deployed config — the original "zero telemetry" result was specific to a scan where nearly every connection timed out (Sysmon only logs established connections, per Microsoft's own guidance). Telemetry now exists for the narrow case of successful connections, which is enough to support a forensic investigation — hence 0, not -1 — but it carries a generic PowerShell-network-activity tag rather than a discovery-specific one, and a Wazuh alert search still returns zero results. The technique remains functionally undetected; only the DeTT&CT category changed, not the practical outcome.
- **T1003.001's "why" column corrected**, not rescored. The finding's original claim that no ImageLoad rule existed for `comsvcs.dll` was wrong — Compound Rule 0096 was already present in this lab's Balanced Sysmon config. The score stays N/A (the technique still never reached LSASS memory), but the underlying finding is more complete: the real gap was a Wazuh ruleset gap (Event 7 telemetry exists and reaches Wazuh; nothing inspected it).
- **T1003.001's Wazuh ruleset gap closed.** Rule 100240 was deployed and verified live in a later session, inspecting the Event 7/`comsvcs.dll` telemetry Compound Rule 0096 produces. The technique's *attempt* (comsvcs.dll+rundll32 execution) is now detected at the Wazuh layer regardless of whether `RunAsPPL` subsequently blocks the memory-access step. The score remains N/A — this scale measures detection of the credential-access step itself, which still never occurs — but the finding document now reflects that the attempt is no longer silently unobserved.

## T1046 — a legitimate case for DeTT&CT's per-data-source scoring, not a single number

DeTT&CT explicitly supports scoring visibility and detection **per data source**, not just per technique — this is exactly the right tool for T1046's actual result. Scored as one number, T1046 would misleadingly read as either "fully missed" (ignoring that the network perimeter genuinely reacted) or "caught" (ignoring that the SIEM has no record of it). The honest breakdown:

- **Endpoint / Sysmon data source: 0 / Forensics / context** (revised — see Update above). Event 3 now generates for genuinely successful connections, but carries no discovery-specific tag and produces zero Wazuh alerts — logged, not detected.
- **Network / Suricata data source: functionally effective, but unscored here.** Suricata's ET SCAN ruleset detected the activity and a real, automated response chain (Wazuh rule 100100 → Shuffle → OPNsense block → TheHive case #1024, confirmed live) executed correctly and in real time. This isn't scored on the 5-point scale above because the missing piece isn't detection quality or even documentation — a human-visible case record does exist — it's *correlation*: Wazuh itself cannot show "this alert led to this containment outcome" as one linked record on its own, since the outcome lives in TheHive (see the [T1046 finding](https://github.com/k0zzi/soc-lab-portfolio/blob/main/tools/red-team/findings/T1046.md) for the specific gaps — one of which, OPNsense filterlog forwarding, has since been closed in a later remediation session; a second, small-scope fix now writes the originating Wazuh rule ID and alert ID directly into the TheHive case description, closing most of the remaining correlation gap). A technique can be effectively detected and its response genuinely documented, and still have had a cross-tool correlation gap; DeTT&CT's scale measures detection quality, not tool integration.
